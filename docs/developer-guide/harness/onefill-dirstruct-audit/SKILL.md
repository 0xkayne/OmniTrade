# 核对目录结构与源码是否一致

## 这个 skill 存在的理由

[代码目录结构规范](../../standards/directory-structure.md) §10 的规则**已经由
`tests/test_architecture.py` 每次 `pytest` 断言**，这部分不需要人工核对。这个 skill 核对的是
机器断言覆盖不到的那一半。

机器抓得住一条非法的 import，抓不住的是：**规范里写的目录树和边集，是否还是代码的那个**。
§4 的目标目录树、§5 的「收 / 不收」清单、§7 的超限文件清单，都是**手写的断言**——
新增一个模块后忘了同步 §4，规范就成了一份描述从前的系统的文档，而它看起来仍然完整。

而它会被当作依据使用：§1 的三条问题（模块属于哪一层、允许依赖谁、能否安全删除）
只在**下一次改动的落点判断**中被使用。规范写的结构与代码的实际结构一旦分叉，
判断会持续出错，而且没有任何机制会提示。

## 先读规范，不要背清单

核对对象与判定依据全部写在 [代码目录结构规范](../../standards/directory-structure.md) 里。
**不要在这里复制目录树或边集**——它们是规范正文，复制出来的第二份会在下次结构调整时腐烂。

| 读什么 | 为什么 |
|---|---|
| §3 分层模型与允许边集 | 机器已断言，核对时只需确认它**仍覆盖**新模块 |
| §4 目标目录树 | **手写断言**：新模块是否已登记 |
| §5 各目录收录规则 | 新文件是否落在「收」的范围内 |
| §6 依赖规则 | 新增边是否已在表内（机器会拦，但要先改规范） |
| §7 文件与目录命名、超限清单 | 手写的行数数字会漂 |
| §8 测试目录对应关系 | 新模块的测试是否落在镜像位置 |
| §9 迁移记录 | 是否残留已完成事项 |

条目 schema 与记录格式见 [漂移台账协议](../drift-ledger/PROTOCOL.md)。

## 核对流程

### 第一步：圈出本次的结构性改动

```bash
# 新增/删除/移动了哪些文件
git diff --name-status --diff-filter=ADR

# 结构性改动最直接的信号：出现了新的跨包 import
git diff -U0 -- 'src/**/*.py' | grep -E '^\+.*(from|import) src\.'
```

### 第二步：跑机器断言，再看手写断言

```bash
./scripts/verify.sh arch
```

`tests/test_architecture.py` 会断言：允许边集是否封闭、import 图是否有环、
`persistence/` 是否是叶子、import 期是否无副作用、`config/` 是否只在 `src/cli/` 读、
公开符号是否唯一。**它失败时不要去改测试**——它报的是规范被违反，先改规范或改代码。

这一步过了之后，核对机器抓不住的部分：

| 核对对象 | 判定依据 |
|---|---|
| §4 目录树 | 源码里的每个包/模块是否都在树上；树上是否还有已删除的 |
| §5 收录规则 | 新文件是否落在该目录「收」的范围内，是否踩了「不收」 |
| §7 超限清单 | 清单里的行数是否仍准确；是否出现了新的超限文件 |
| §8 测试镜像 | 新模块的测试是否落在镜像位置，而不是新建类型目录 |
| §9 迁移记录 | 是否残留已完成的迁移项（它记录的是「做过什么」，不是「现状」） |

**§4 的目录树是最常漂的一处**，因为新增模块时它不会报错，只会慢慢变得不完整。

### 第三步：写下应波及的断言，再核对

**先写下来，再核对。** 不写的话核对会退化成把规范重读一遍——而重读对已经失效的断言
没有任何作用，因为**失效的断言读起来和有效的一样**。

### 第四步：偏差只产出条目草案

条目 schema、三类回流判定、记录格式全部见 [漂移台账协议](../drift-ledger/PROTOCOL.md)。
**不要就地改规范**——就地修改会让漂移本身失去记录价值。

## 特别提醒：区分「现状」与「目标」

规范 §9 显式声明了「当前代码符合本文档」。**写这条声明的前提是它仍然为真。**
一旦核对发现代码与规范不符，要么改代码，要么把 §9 的声明改成「本文档描述的是目标结构」
并列出实测偏差——不得让一份混合了「应该怎样」与「实际怎样」的文档被读成对现状的描述。

## 什么不在这个 skill 的范围里

- **符号命名**是否符合命名规范 —— `onefill-naming-audit`
- **`docs/` 的整体一致性**与文档数字 —— `onefill-docs-audit`
- **架构图与设计文档的双向对账** —— `onefill-arch-audit`

分工重叠会让两处都以为对方在管。只核对本文件列出的这几类。
