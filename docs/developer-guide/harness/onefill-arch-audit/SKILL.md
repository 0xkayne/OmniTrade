# 核对架构文档与源码是否对账

## 这个 skill 存在的理由

架构文档最大的风险不是**写错**，而是**写对之后代码变了**。

而读图的人正是依据图来判断改动落点的——一张失效的图会让每一次判断都错在一个看不见的地方。
`meta-skills/1-architecture-analysis/architecture-analysis.md`（架构分析范式） §7 已经写明
「不一致要可发现，靠的是重绘触发这类约定」——**但约定不会自己触发**。
这个 skill 是那个约定的执行者：§7 回答「什么时候该重绘」，核对回答「怎么发现它已经该重绘了」。

## 先读范式，不要背清单

核对对象与判定依据写在 `meta-skills/1-architecture-analysis/architecture-analysis.md`（架构分析范式） 里。
**不要在这里复制那份骨架**——它是范式正文，复制出来的第二份会在范式调整时腐烂。

| 读什么 | 为什么 |
|---|---|
| §7 与代码的一致性 | 双向对账与重绘触发的定义 |
| §5 的 workflow 骨架 | 八段是否齐全、「不负责什么」一列是否非空 |
| §4 的图规则 | 节点是否对应真实符号、边是否都有语义标注 |
| §10 验收 | 一份合格的产出要满足的全部条件 |

条目 schema 与记录格式见 [漂移台账协议](../drift-ledger/PROTOCOL.md)。

## 核对流程

### 第一步：确认重绘触发是否已经发生

范式 §7 列出三类触发条件。先判定本次改动是否命中：

- 涉及该模块的变更被合入
- 组件职责边界变化
- 不变量或失败门禁增减

命中哪一份文档，由 `applies_to` 反查：

```bash
grep -l 'src/coordinator' docs/developer-guide/design/*.md
```

### 第二步：双向对账，两个方向都要走

| 方向 | 检查什么 |
|---|---|
| **图 → 源码** | 图上每个节点是否仍对应可定位的真实符号；是否出现未标注的边 |
| **源码 → 图** | 读者需要知道的符号是否都在图上或文档中有位置 |

第二个方向最容易被跳过，但它才是发现「新模块没进图」的唯一手段——
只走第一个方向，图会一直正确，只是缺东西。

### 第三步：核对骨架与断言

| 核对对象 | 判定依据 |
|---|---|
| 骨架完整性 | §5 的八个段落是否齐全，「不负责什么」一列是否非空 |
| 职责边界 | §5 第 4 节的职责表与图上的模块边界是否仍一致 |
| 不变量与失败门禁 | §5 第 6、7 节列出的约束是否仍成立、是否增减 |
| 范围声明 | 文档记录的代码版本与未覆盖范围是否仍然准确 |
| 硬编码数字 | 行数、类数等——**发现就换成命令或删掉**，不要更新成新数字 |
| 同一事实的多个副本 | 同一张图/同一张表是否在多处各有一份且已分叉 |
| `.dot` 与 `.svg` 是否同步 | `./scripts/render_diagrams.sh --check`——机器可判，不必手查 |

最后一行的分界要说清楚：**`--check` 只保证 `.svg` 是 `.dot` 渲染出来的那一个，
不保证 `.dot` 描述的还是代码里那个系统。** 前者是「生成物与源码一致」，
后者是「图与代码对账」——那正是本文 §第二步双向对账在做的事。两者不可互相替代。

最后一行在这个仓库里已经有实例：状态机曾经在 `sys-architecture.md` 与
`base-state-machine.md` 各画一份，两份后来漂成了不同的写法。**发现同一事实有多个副本时，
正确的处置是留下权威的那一份、其余改为链接**，而不是把两份都更新一遍。

### 第四步：写下应波及的断言，再核对

**先写下来，再核对。** 不写的话核对会退化成把文档重读一遍——而重读对已经失效的断言
没有任何作用，因为**失效的断言读起来和有效的一样**。

### 第五步：偏差只产出条目草案

条目 schema、三类回流判定、记录格式全部见 [漂移台账协议](../drift-ledger/PROTOCOL.md)。
**不要就地改图或改文档**——范式 §7 明确要求「记录信号，不就地修改」，
就地修改会让漂移本身失去记录价值。

## 什么不在这个 skill 的范围里

- **文档的数字、元数据、死链** —— `onefill-docs-audit`
- **目录结构与依赖边** —— `onefill-dirstruct-audit`
- **符号命名** —— `onefill-naming-audit`

分工重叠会让两处都以为对方在管。只核对本文件列出的这几类。

## 伴生件的元数据

本文件是 skill，不是 `docs-paradigm.md` §4 意义上的正式文档：frontmatter 的字段集合是封闭的，
五个文档字段挂在 `metadata:` 下。改动后用校验脚本验证：
