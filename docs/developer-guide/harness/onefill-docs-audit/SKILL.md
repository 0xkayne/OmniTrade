# 核对 docs/ 与代码是否一致

## 这个 skill 存在的理由

`docs/docs-paradigm.md` §9 列了一份提交前检查清单。它的问题是**由「记得检查」触发**——
而文档失效的原因通常不在文档侧：**代码变了，文档没变**。

这类失效不产生任何信号。`mkdocs build --strict` 抓得住死链和孤儿页，因为那是机械的；
但一句格式完好、只是不再成立的断言（「测试收集数为 455」「路径是 `src/core/`」）不会被任何
检查发现。读文档的人不会去验证文档——他会照着做，做错之后也不会回头怀疑文档。

所以这个 skill 的触发点是**事件**（一次功能开发完成），不是记性。

## 先读规范，不要背清单

核对对象与判定依据全部写在 [docs-paradigm.md §10](../../../docs-paradigm.md) 的表里。
**不要在这里复制那张表**——它是规范正文，复制出来的第二份会在规范调整时腐烂，
而且没有任何检查会发现（这正是规范 §7 对本目录的要求）。

你要读的是这三处：

| 读什么 | 为什么 |
|---|---|
| `docs-paradigm.md` §10 的核对对象表 | 本次要逐条核对的清单 |
| `docs-paradigm.md` §4 | 元数据的五个字段与 `applies_to` 的要求 |
| `docs-paradigm.md` §5 | 生命周期：该改、该重写、还是该删 |

## 核对流程

### 第一步：写下这次改动**应该**波及哪些断言

强制产出，且必须写下来。不写的话，核对会退化成把文档重读一遍——而重读对已经失效的断言
没有任何作用，因为**失效的断言读起来和有效的一样**。

用 `applies_to` 反查，它写的就是文档覆盖的源码路径：

```bash
# 这次改了 coordinator，哪些文档声称覆盖它？
grep -l 'src/coordinator' docs/developer-guide/design/*.md

# 改了公开符号名或后缀？命名规范的登记表要一起核对
grep -l 'src/' docs/developer-guide/standards/*.md
```

改动清单从 `git diff --name-only` 取，不要凭印象回忆——一次功能开发往往碰了比你以为更多的文件。

### 第二步：逐条核对

对第一步圈出的每份文档，把其中的断言逐条对照。断言有三种可定位形式，核对方式各不相同：

| 断言形式 | 怎么核对 | 例 |
|---|---|---|
| 指向源码位置 | 路径/符号是否仍存在 | 「`QuoteFetcher` 在 `market/quote_fetcher.py`」 |
| 指向可执行命令 | 命令是否真能跑通 | 「`pytest --collect-only -q` 复核测试数」 |
| 指向可解析路径 | 文件是否存在 | `design/*.md`、`CLAUDE.md` 里的入口指针 |

跑一遍 `./scripts/verify.sh docs` 覆盖其中的机械部分（死链、孤儿页、导航）。

**核对结果有三种，不是两种**：吻合 / 不符 / **无法核对**。定位不到的断言单列出来，
**不上报为偏差**——无法核对和与实现不符是两件事，混在一起会让偏差清单被噪音淹没。

### 第三步：区分「过时」还是「一次性」

发现的每一处不符，判定它属于哪一类——这个判定决定处置方式：

| 判定 | 判据 | 处置 |
|---|---|---|
| 文档过时 | 换一台机器、换一个人重来，问题还在 | 记条目 + 改文档正文 |
| 环境变化 | 上次成立是因为当时的某个外部条件 | 记条目 + 更新环境段 |
| 一次性问题 | 只是这次任务恰好如此 | 记录但**不入索引**（有意遗忘） |

区分前两者的办法很直接：**换一台机器重跑，问题还会出现吗？** 会 → 文档过时。

### 第四步：偏差只产出条目草案

**不要就地改文档。** 就地修改会让漂移本身失去记录价值——下次从同一个地方再踩一次，
而没有任何记录说明上一次踩过。

产出条目草案，由人判定后执行。每条草案要能回答：改哪个文件、哪一段断言、改成什么、
依据是哪一行源码或哪条命令。

### 第五步：留下核对记录

强制产出，四段：

```text
本次功能开发改动了什么 / 产物中哪些断言因此需要复核 /
逐条核对结果（吻合 / 不符 / 无法核对）/ 本次使用的知识条目
```

第二段是重点。它把「这次改动应该波及哪些断言」显式写下来，否则核对会退化成重读一遍。

## 已知的腐烂热点

这几个地方以前烂过，每次都主动看一眼——它们有一个共同点：**描述的是某个时刻的状态**。

| 热点 | 在哪 | 为什么容易烂 |
|---|---|---|
| 行数、测试数等硬编码数字 | 任意文档正文 | 改一行代码就过期，且同一组数字常被手写在多处 |
| 目录树 | `standards/directory-structure.md` §4 | 新增/移动模块后不同步更新 |
| 符号清单与「现有」列 | `standards/naming-conventions.md` §5、§6 | 新增类/后缀后没有回填 |
| CLI 命令列表 | `reference/current-status.md` | 加一个 Typer 命令就过期 |
| 跨文件指针 | `CLAUDE.md`、`developer-guide/index.md` | **纯文本路径，mkdocs 看不见**，改名后不会报错 |
| 同一事实的多个副本 | 例如状态机出现在三处 | 改一处漏两处，两个都像正确答案 |

**数字不要手写。** 测试数、行数这类东西的正确做法是让文档指向命令而不是抄结果——
`reference/current-status.md` 已经这么做了（给出 `pytest --collect-only -q` 让读者自己复核）。
发现别处还在手写数字时，把它删掉换成命令，比更新成新的数字更有价值。

## 什么不在这个 skill 的范围里

- **跨层依赖边、循环导入、`persistence/` 叶子性、公开符号唯一性、凭据外泄**——
  这些由 `tests/test_architecture.py` 在每次 `pytest` 时断言，不需要人工核对。
  `harness/index.md` §5 列出了机器保证与判断覆盖的分界。
- **命名是否规范**——那是 `onefill-naming-audit` 的范围。
- **目录结构是否符合规范**——那是 `onefill-dirstruct-audit` 的范围。
- **架构图与设计文档是否与源码对账**——那是 `onefill-arch-audit` 的范围。

分工重叠会让两处都以为对方在管。只核对本文列出的这几类断言。

## 伴生件的元数据

本文件是 skill，不是 `docs-paradigm.md` §4 意义上的正式文档：frontmatter 的字段集合是封闭的，
多一个键就装不上。五个文档字段挂在 `metadata:` 下，因此校验脚本不会拒绝它。

改动本文件后，用 skill 校验脚本验证：

```bash
uv run --locked python scripts/validate_skills.py
```
