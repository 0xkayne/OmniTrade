# 漂移台账协议

本目录是 Omnitrade 所有伴生 skill 的**唯一知识库**。它们共用这一套条目 schema、状态机、
索引与回流判定，因此这些内容只在这里定义一次——每个伴生 skill 只写自己「核对什么、怎么核对」，
不重复本文件的内容。

这份约束来自 `meta-skills/7-skill-rsi/skill_self_optimization.md`
的「核心原则：单一知识源」：约束知识只存一处，skill 通过标识引用它，不复制内容。
复制出来的第二份会在下次调整时腐烂，而且没有任何检查会发现——这与文档腐烂是同一个病。

## 存在的理由

文档、图、规范表、skill 都是对项目状态的**断言**。断言失效时不会报错：读者照着它去做，
做错之后也不会回头怀疑它。`mkdocs build --strict` 能抓死链，因为那是机械的；抓不住
「链接还在，只是不再成立」。

台账的作用不是「记住更多」，而是让**「产物与实际不符」变得可见且必然被处理**。

## 两种伴生件

|  | 核对型 | 自进化型 |
|---|---|---|
| 被优化对象 | **断言**：文档、图、规范表 | **流程**：一份可执行的 skill |
| 对应范式 | 0- / 1- / 2- / 3- | 4- / 5- |
| 触发时机 | **每次功能开发完成后** | 流程运行中，以及每次流程结束时 |
| 产出 | 断言逐条与项目实际对照，产出偏差条目 | 挂捕获点，把运行中发现的约束回流 |

判据按**主产物**定：主产物是流程还是断言。

## 条目 schema

每条约束一个文件，文件名 `<标识>.md`，标识形如 `DRIFT-0007`。

```yaml
---
id: DRIFT-0007
date: YYYY-MM-DD
category: <见下方封闭集合>
severity: low | medium | high
status: <见状态机>
trigger: <什么条件下会撞上它>
tags: [<泛化标签，用于聚合>]
found_by: <核对型 | 自进化型> / <skill 名>
applies_to: <适用的版本 / 分支 / 对象范围>
revalidate: <一条可执行命令>
last_verified: YYYY-MM-DD
---
```

`applies_to` / `revalidate` / `last_verified` 三个字段补的是同一个缺口：
**只有「废弃」一个终态的知识库会静默过期**——没有「何时该重新验证」「适用于哪个版本」，
条目会一直看起来有效。

正文段落（顺序固定）：

1. **问题描述** —— 现象 / 根因 / 表现
2. **约束定义** —— 必须满足的条件 / 违反后果 / 评估方法（**必须是可执行命令**）
3. **代码位置** —— 可定位的源码符号或路径
4. **标准解决方案** —— 正确做法 / 常见错误做法
5. **关联条目** —— 用标识引用，不复制内容
6. **发现过程** —— 哪次开发、什么信号触发的

## 状态机

```text
种子 → 探索中 → 已发现 → 约束已定义 → 已自动化 → 已验证 → 已废弃
```

**补充流转**：`revalidate` 命令执行失败，或 `applies_to` 不再覆盖当前版本时，状态**回退**，
并在索引中标记为待处理。这把「过时」从静态标记变成了可发现事件。

## 索引

`INDEX.md` 维护五节：统计 / 条目表 / 来源统计 / 泛化标签索引 / **依赖关系**。

依赖关系是最有价值的产出：单条约束是碎片，依赖链才是知识。建立若干条目之后主动整理一次。

**闭环指标**（用于观察这套机制是否在工作）：

| 指标 | 期望方向 |
|---|---|
| 条目命中率 | 上升 |
| 新条目产生速率 | 下降（说明覆盖度提升） |
| 同类任务第二次耗时 | 下降 |
| 探针失败率 | 降至零并保持 |
| **漂移类型集中度** | 最大一类的占比——高占比提示该段写法需**结构性重写** |

最后一项把「处理每条漂移」提升为「处理漂移的类别」，是从打补丁走向改设计的关键。
连续失败比单次失败更重要：同一类位置上反复漂移，说明当初就不该写死。

## 记录的格式（强制产出）

两类伴生件都必须留下记录。**第二段是重点**——不写它，核对会退化成把产物重读一遍，
而重读对已经失效的断言没有任何作用。

**核对型的四段：**

```text
本次功能开发改动了什么 / 断言中哪些需要复核 /
逐条核对结果（吻合 / 不符 / 无法核对）/ 本次使用的条目
```

**自进化型的五段：**

```text
实际执行范围 / 复用的历史产物 / 失败与终止 /
与 skill 描述不符之处 / 本次使用的条目
```

自进化型的第四段是重点：「绕过 skill 的做法」在当次运行中不产生任何失败，因而不会被自动记录，
但它精确标记了 skill 的过时点。把它规定为强制，是让过时变得可见的主要手段。

## 回流的三类判定

| 判定 | 判据 | 处置 |
|---|---|---|
| 产物过时 | 换一台机器、换一个人重来，问题还在 | 记条目 + 改产物正文 |
| 环境变化 | 上次成立是因为当时的某个外部条件 | 记条目 + 更新环境段与 `revalidate` |
| 一次性问题 | 只是这次任务恰好如此 | 记录但**不入索引**（有意遗忘） |

前两者的区分办法很直接：**换一台机器重跑，问题还会出现吗？** 会 → 产物过时。

**有意遗忘是必要的**：自动创建的条目会稀释知识库，一个充满噪音的库和一个空库一样没用。
被拒绝的条目及其理由要留下记录，否则同一件事会被反复提案。

## 漂移探针

有些漂移不会在运行中被发现——本次任务恰好复用了旧产物，没走到出问题的那一步。
探针主动检查产物中硬编码的事实：路径是否存在、入口是否仍支持所写的参数、
文档中的符号是否仍可定位、当前版本是否仍在 `applies_to` 范围内。

- 探针必须**只读**，且在任何耗时操作之前运行。
- 探针失败时**不自动修改**产物，而是产出条目草案，交人判定。
- **连续失败比单次失败更重要**：它说明某一段的写法有结构性问题，处置应从「打补丁」上升到「改设计」。

## 两条硬规则

**偏差只产出条目草案，不就地修改。** 就地修改会让漂移本身失去记录价值，而且执行者并不具备
判断「这是过时、环境变化还是一次性问题」所需的全部信息。改产物由人判定后执行。

**定位不到的断言单列，不上报为偏差。** 无法核对和与实现不符是两件事，混在一起会让偏差清单
被噪音淹没。这类断言单独列出，标为「无法核对」。

## 当前状态

台账为空，这是正常的起点，不是失败。条目随每次开发完成后累积；
`INDEX.md` 的「条目表」为空时才说明这套机制尚未被使用过。
