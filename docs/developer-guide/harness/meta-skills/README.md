# 新功能开发自动化体系

一套把「自动为项目扩展新功能」拆成四个可独立建设、又互相咬合的子系统的方法。

| 子系统 | 解决的问题 | 文档 |
|---|---|---|
| 认知层：架构图 + workflow 解释文档 | 系统链路过长，context window 限制下对系统理解不完整 | [1- architecture-analysis.md](1-architecture-analysis/architecture-analysis.md) |
| 执行层：固定流程自动化 skill | 重复固定流程人工处理时的时间开销与不确定性 | [4- fixed_procedure_skill.md](4-fixed-procedure/fixed_procedure_skill.md) |
| 生成层：非固定流程 skill 与元 skill | 人类尚未掌握的流程无法自动化 | [5- flexible_procedure_skill.md](5-flexible-procedure/flexible_procedure_skill.md) |
| 演化层：伴生件（自进化 / 核对） | 0~5 的产物都会过时，且失效时不报错 | [7- skill_self_optimization.md](7-skill-rsi/skill_self_optimization.md) |

`0-`、`2-`、`3-` 不占闭环的一段：它们是**贯穿各层的约束**（文档怎么写、名字怎么起、目录怎么分层），在认知、执行、生成三层的产物上同时生效，见下一节。

## 目录与使用方式

| 目录 | 作用 | 何时使用 | 产出 |
|---|---|---|---|
| `0-docs-paradigm/` | 文档系统的编写规范：`docs/` 布局、命名、元数据、权威级别、生命周期 | 建立或改动文档系统时；任何文档变更都以它为准 | 项目的 `docs/` 体系本身 |
| `1-architecture-analysis/` | 开发前的架构分析方法：分析什么、产出什么、放在哪里、如何与代码保持一致 | **任何模块级功能开发开始之前**；纯文档、纯注释的改动不触发 | 一张图 + 一份 workflow 文档（成对） |
| `2-naming-convention/` | 命名规范：符号形态、词根、术语唯一性、保留后缀、例外登记 | 制定命名规范时；**新增公开符号之前**按定名流程逐条查 | 项目的《命名规范》 |
| `3-directory-paradigm/` | 目录结构规范：分层模型、允许边集、隔离区、迁移路径 | 制定结构规范时；新增模块、调整目录时 | 项目的《目录结构规范》 |
| `4-fixed-procedure/` | 把一条**判据已经能写清**的重复流程固化成 skill | 流程已被人工走通，且「重跑 / 复用」的边界能从改动清单判定时 | 固定流程 skill + 自进化伴生 skill |
| `5-flexible-procedure/` | 把一块**人类尚未掌握**的领域固化成探索 skill 与知识库 | 目标已知、步骤未知，需要反复探索且要让经验可积累时 | 主流程 skill + 伴生 skill（一个 plugin） |
| `6-design-pattern-paradigm(unused)/` | 领域设计模式知识 | 暂未启用，不计入下面的闭环 | — |
| `7-skill-rsi/` | 各范式产物的**伴生件**机制：自进化型与核对型 | 生成 4- / 5- 的 skill 时；每次功能开发完成后核对 0~3 的产物时 | 伴生 skill |

### 它们是范本，不是手册

**0~5 每一份都是生成器。** 把它连同你的具体场景交给 AI，产出的是**你的项目自己的**那份规范、流程或 skill，而不是照搬文档内容。每个目录下的 `examples/` 是一份已经完成的实例化，用来校准产出的粒度与信息密度——产出的东西应当与样例处于同一量级，而不是更粗略。

**这棵 `meta-skills/` 是项目启动之初一次性使用的引导材料，不是项目的日常文档。** 它随项目一起入库，但**建成之后就不再更新**——它的内容对应的是「建设这套体系」这一刻的场景，而不是项目后来的实际形态。判断一份文件属于哪一类，看它回答的是哪个问题：

| 问题 | 归属 | 例 |
|---|---|---|
| 「怎么把一套 AI 开发体系建起来」 | `meta-skills/`（范本，冻结） | `0-docs-paradigm/docs-paradigm.md` |
| 「Omnitrade 这个项目当前的规范是什么」 | `docs/` 根 与 `standards/`（产物，持续更新） | `docs/docs-paradigm.md` |

**因此同名文件的两份副本不是分叉，是范本与产物。** `meta-skills/0-docs-paradigm/docs-paradigm.md` 是产出 `docs/docs-paradigm.md` 的那份范本；后者的内容随项目演进，前者不会跟着变。两者不一致时以**产物**为准，不要把改动回灌进范本——回灌会让范本失去「当时是怎么建起来的」这个唯一价值。

同理，每个范本 §「存放」里写的目录名是**范本给出的建议值**（例如 `harness/`），项目实际采用的名字以项目的 `docs/docs-paradigm.md` §2 为准。

`7-skill-rsi/` 不生成独立产物。它为上面每一份产物生成一份**伴生 skill**：产物是流程（4- / 5-）时用自进化型，产物是断言（0~3 的文档、图、规范表）时用核对型。

### AI 的使用顺序

```text
开始编码前      1- → 产出或更新目标模块的架构图与 workflow 文档
                先读 0- 与 docs/developer-guide/ 下该模块的 design 文档，不要从读代码开始
写代码时        2- 与 3- 的规则；新增公开符号走 2- 的定名流程
固化一类工作     判据能写清 → 4-；写不清 → 5-
每次开发完成后   跑 7- 生成的核对型伴生 skill，核对 0~3 的产物与实际是否吻合
```

### 权威顺序

源码、配置文件与测试 > `authority: normative` 的开发文档 > `authority: reference` 的用户/API 文档 > `authority: proposal` 的设计文档。

源码与文档冲突时，以源码为准，并修正文档或明确记录代码缺陷——**不得在文档中保留两个都像正确答案的说法**。完整规则见 [docs-paradigm.md](0-docs-paradigm/docs-paradigm.md) §3。

## 闭环

```text
[1-] 认知层 ──作为纲领注入──► [5-] 生成层
                                │
                                │ 提取验收指标与采集方式，固化
                                v
                              [4-] 执行层
                                │
                                │ 每次应用产出应用记录
                                v
                              [7-] 演化层
                                │
                                └──► 回改 认知 / 执行 / 生成
```

四个子系统不是四个平行的建议，而是同一条闭环上的四段。三条不变量：

1. **生成层消费认知层、产出执行层。** 生成的开篇是架构探索，结尾是验收指标提取；提取结果必须以执行层的形态落地，否则验收会退化成一次性人工判读。**这条链上的每一环都受 `0-`、`2-`、`3-` 的约束**，它们不占闭环的一段。
2. **演化层不是第四个产物，而是伴生件。** 0~5 每一个范式的产物都要配一份由 `7-skill-rsi/` 生成的伴生 skill。产物是**流程**（4-、5-）时用自进化型，产物是**断言**（0-、1-、2-、3- 的文档、图、规范表）时用核对型。没有回流通道的产物，其有效期等于下一次变更的时间。
3. **单一知识源。** 知识只存一处，skill 通过标识引用它而不复制内容。这是演化层能成立的前提。

## 执行者分工

| 子系统 | 能力要求 |
|---|---|
| 认知层（1-） | 深度探索能力强，对已有系统进行探索时不易漂移 |
| 执行层（4-） | 创新性弱但循规蹈矩——流程已固定，严格执行判据是首要品质 |
| 生成层（5-） | 自主思考能力强，处理的是人为未掌握的问题 |
| 演化层（7-） | 自主思考能力强，需要判断「与实际不符」属于过时、环境变化还是一次性问题 |

## 落地顺序

**执行层 → 演化层 → 认知层 → 生成层。**

执行层最容易已有可反推成模板的现成实现，收益立即兑现；演化层紧随其后，因为执行层一旦被复制就会立刻面临过时问题；认知层可以独立服务任何读者，能并行推进；生成层价值上限最高，但对前三者的完备度依赖最强，过早建设只会得到一份无法被验证的产物。

## 共享的验证共识

凡是能自动生成的产物（图、索引、覆盖清单），都应有一个可执行的重新生成入口；凡是不能自动生成的（职责表、失败门禁），都应有一条可执行的交叉校验命令。做不到这一点的文档类产物，会在若干次变更后静默失真。
