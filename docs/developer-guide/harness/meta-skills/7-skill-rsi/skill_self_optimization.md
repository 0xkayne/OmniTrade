# Skill 自我优化与产物核对

## 目的

无论是 skill 还是描述性产物（文档、图、规范表），都会过时。危害不是「不好用」，而是**准不准不会被发现**——过时的路径、命令、契约会产出看起来正常但实际错误的结果；过时的文档与图会让读者据此持续做出错误判断，而错误不会以任何方式提示自己存在。

因此产物不是「更好的 skill」或「更准的文档」，而是一条让「产物与实际不符」变得**可见**、且**必然被处理**的通道。

## 伴生件的两种角色

被优化的对象有两种形态，伴生件因此有两种角色。两者的知识库、管理器、条目 schema、生命周期、索引与回流判定是**同一套**；不同的只有**触发时机**与**产出**。

|  | 自进化型 | 核对型 |
|---|---|---|
| 被优化对象 | **skill**——一份可执行的流程 | **描述性产物**——对项目状态的断言（文档、图、规范表） |
| 适用范式 | [4-](../4-fixed-procedure/fixed_procedure_skill.md)、[5-](../5-flexible-procedure/flexible_procedure_skill.md) | [0-](../0-docs-paradigm/docs-paradigm.md)、[1-](../1-architecture-analysis/architecture-analysis.md)、[2-](../2-naming-convention/naming-conventions.md)、[3-](../3-directory-paradigm/directory-structure-paradigm.md) |
| 触发时机 | 流程运行中，以及每次流程结束时 | 每次功能开发完成后 |
| 伴生件做什么 | 在流程中挂捕获点，把运行中发现的新约束与「与描述不符之处」回流 | 把产物中的断言逐条与项目实际对照，产出偏差条目 |
| 产出 | 条目草案 + 对 skill 正文的修改建议 | 条目草案 + 对产物正文的修改建议 |
| 谁来改正文 | 管理器判定后执行；伴生件只产生草案 | 同左 |

**判据**：主产物是一份**可执行的流程**时用自进化型；是对**项目当前状态的断言**时用核对型。两者都像时按主产物定——skill 是流程，文档与图是断言。

**核对型的额外约束：断言必须可被定位。** 核对的对象是产物里写下的每一句「当前 / 默认 / 支持 / 保证」，它们必须各自指向一个可读取的源码位置、一条可执行的命令或一个可解析的路径。定位不到的断言无法被核对，只能被重读一遍——这类断言在核对清单中**单列**，**不上报为偏差**：无法核对和与实现不符是两件事，混在一起会让偏差清单被噪音淹没。

## 核心原则：单一知识源

约束知识只存一处，skill 通过标识引用它，不复制内容。这样约束变更时 skill 自动保持正确。

**这条原则决定了改哪里：**

| 变了什么 | 改哪里 |
|---|---|
| 约束本身 | 知识条目 |
| 约束该由谁负责 | 路由表 |
| 流程步骤 | skill 正文 |

**内容边界判据：**

- 已经存在于知识条目中的文字 → 不在 skill 中重复。
- 描述「如何做分析」而非「分析发现了什么」 → 属于 skill。
- 只在特定上下文中有意义 → 属于更具体的 skill。

## 三件套

| 组件 | 职责 |
|---|---|
| 知识库 | 每条约束一个文件 + 一份索引 |
| 管理器 | 唯一有权写约束、改路由、判定废弃的组件 |
| 伴生 skill | 自进化型：在被优化 skill 的运行流程中挂载捕获点与结束时的回流步骤；核对型：在每次功能开发完成后把产物的断言与实际项目逐条对照 |

**伴生件不可省。** 没有捕获点，运行过程中产生的「这里有约束」这个信息不会留下记录，下次从头再踩一遍；没有核对，产物中已经失效的断言不会被任何一次运行暴露——**读文档的人不会去验证文档**。

## 知识条目的字段

标识、日期、分类、严重度、状态、触发条件、泛化标签、发现者，加上：

- **适用范围** —— 适用的版本 / 分支 / 对象范围
- **重新验证** —— 一条可执行命令
- **最后验证** —— 日期

正文段落：问题描述（现象 / 根因 / 表现）、约束定义（必须满足的条件 / 违反后果 / 评估方法——必须是可执行命令）、代码位置、标准解决方案（正确做法 / 常见错误做法 / 自动化建议）、关联条目、发现过程。

后三个字段补的是同一个缺口：**只有「废弃」一个终态的知识库，没有「何时该重新验证」「适用于哪个版本」，条目会静默过期。**

## 生命周期

```text
种子 → 探索中 → 已发现 → 约束已定义 → 已自动化 → 已验证 → 已废弃
```

**补充流转**：重新验证命令执行失败，或适用范围不再覆盖当前版本时，状态**回退**，并在索引中标记为待处理。这把「过时」从静态标记变成了可发现事件。

## 索引

统计、条目表、来源统计、泛化标签索引、依赖关系。

**依赖关系是最有价值的产出。** 单条约束是碎片，依赖链才是知识。建立若干条目之后应主动整理一次，把碎片串成链。

## 捕获时机

**显式信号** —— 使用者明确表述「这里容易出错」「必须满足」「如果不 X 就会 Y」这类因果描述。应当**主动提议**记录。

**隐式信号** —— 反复调试才通过、依赖链比预期复杂、存在只写在代码里的约定。**建议记录，但不自动创建**。

**运行产物信号** —— 流程执行失败或抛错；skill 描述与实际不符但未导致失败。后者最容易被忽略，因为它不产生任何失败。

**核对信号（核对型）** —— 功能开发完成后，产物中某条断言的定位点已不存在、或定位到的实现与断言不符；以及**产物中不存在、但实际必须遵守的约束**。后一类同样是偏差：规范没写不等于不必遵守，它只说明规范漏了一条。

**信号的不对称性是设计的一部分。** 自动创建的条目会稀释知识库——一个充满噪音的库和一个空库一样没用。

## 应用记录与回流

每次应用结束后，强制产出应用记录，五段：

```text
实际执行范围 / 复用的历史产物 / 失败与终止 / 与 skill 描述不符之处 / 本次使用的知识条目
```

**第四段是重点。** 「绕过 skill 的做法」在当次运行中不产生任何失败，因而不会被自动记录；但它精确标记了 skill 的过时点。把这一段的填写规定为强制，是让过时变得可见的主要手段。

**核对型的记录**同样是强制产出，四段，与上面逐段对应：

```text
本次功能开发改动了什么 / 产物中哪些断言因此需要复核 / 逐条核对结果（吻合 / 不符 / 无法核对）/ 本次使用的知识条目
```

**第二段是重点。** 它把「这次改动应该波及哪些断言」显式写下来，否则核对会退化成把产物重读一遍——而重读对已经失效的断言没有任何作用，因为失效的断言读起来和有效的一样。

回流时逐条判定为三类：

| 判定 | 处置 |
|---|---|
| 产物过时 | 记条目 + 改产物正文：skill 改路由 / 判据 / 步骤，文档与图改断言 |
| 环境变化 | 记条目 + 更新环境段与自检命令 |
| 一次性问题 | 记录但不纳入索引（**有意遗忘**） |

两条规则：

- **区分前两者**：换一台机器重跑，问题还会出现吗？会 → 产物过时。
- **废弃只能由管理器判定**，不能由运行中的 agent 就地判定——就地废弃会让依赖它的条目悄悄悬空。

**有意遗忘**是必要的：否则知识库会被一次性问题淹没。

## 漂移探针

有些漂移不会在运行中被发现——本次任务恰好复用了旧产物，没走到出问题的那一步。探针主动检查 skill 中硬编码的事实：

路径是否存在、入口是否仍支持所写的参数、执行环境是否可起、数据契约是否匹配、文档中的符号是否仍可定位、当前版本是否仍在适用范围内。

- 探针必须**只读**，且在任何耗时操作之前运行。
- 探针失败时**不自动修改 skill**，而是产出条目草案，交管理器判定。
- **连续失败比单次失败更重要**：它说明 skill 的某一段结构性写法有问题（例如路径漂移反复出现在同一类位置上，说明当初就不该写死）。处置应从「打补丁」上升到「改设计」。

## 闭环指标

| 指标 | 期望方向 |
|---|---|
| 条目命中率 | 上升 |
| 新条目产生速率 | 下降（说明覆盖度提升） |
| 同类任务第二次耗时 | 下降 |
| 探针失败率 | 降至零并保持 |
| **漂移类型集中度** | 最大一类的占比——高占比提示该段写法需结构性重写 |

最后一项把「处理每条漂移」提升为「处理漂移的类别」，是这套机制从打补丁走向改设计的关键。

## 组成与存放

伴生件不是独立产物，而是**每一份产物都必须配的搭档**。落地形态按主产物的形态分两种。

**主产物是 skill（4-、5-）时，伴生件与它同处一个 plugin：**

```text
docs/developer-guide/harness/<plugin-name>/
├── .claude-plugin/plugin.json
├── skills/
│   ├── <领域>-<主流程>/SKILL.md   # 由 4- 或 5- 生成
│   └── <领域>-<伴生>/SKILL.md     # 本文档生成
├── references/
│   └── <知识库>/                  # 唯一源
└── legacy/                        # 可选：拆分前的 skill 定义，只读
```

**主产物是描述性产物（0-、1-、2-、3-）时，产物本身是文档或图，没有 plugin 可依附，伴生 skill 独立存放：**

```text
docs/developer-guide/harness/<skill-name>/
├── SKILL.md          # 本文档生成
└── references/       # 可选
```

两种形态的差别只在**住哪里**：条目 schema、管理器、生命周期与闭环指标完全相同。规范正文（文档、图、规范表）留在各自的 `design/` `standards/` 位置，**不搬进 `harness/`**——`harness/` 收录的是服务于 AI 开发流程的 skill，不是产品文档。

**分工不得互相越界。**

| 事项 | 归属 |
|---|---|
| 骨架与阶段划分、已知目录、未知判定与处理协议、真值源、交付物契约、校验门禁、覆盖度与移交 | 主流程 skill（由 4- / 5- 生成） |
| 文档树与元数据、图与 workflow 的骨架、规范正文的登记表与偏差清单、各自的「可执行检查」 | 主产物（由 0~3 生成） |
| 条目字段与状态机、索引结构、捕获点或核对点的位置、漂移探针、回流的三类判定 | 本文档生成的伴生 skill |
| 知识库的物理位置与单一源约束 | 两边共同声明，措辞不得冲突 |

两条与存放有关的硬约束：

- **知识库在 plugin 内只出现一次。** `legacy/` 只存放拆分前的 skill 定义，**不得存放知识库副本**。冻结副本会立刻与持续增长的源分叉；历史条目本来就留在知识库里，不需要第二份。
- **`SKILL.md` 的 frontmatter 是封闭 schema。** 本文档的条目元数据与其他文档一样有五个字段，但写进 `SKILL.md` 时必须挂在 `metadata:` 键下；平铺会让 skill 装不上。skill 元数据 / plugin 清单 / 文档元数据三个 schema 的对照见 [flexible_procedure_skill.md](../5-flexible-procedure/flexible_procedure_skill.md) §6。

## 验收

- 0~5 每个范式的产物都有对应的伴生 skill：4- / 5- 用自进化型，0- / 1- / 2- / 3- 用核对型；或在其正文中有强制的捕获点 / 核对点段落。
- 伴生件的角色与主产物形态相符，判据为「主产物是流程还是断言」。
- 知识库唯一，历史副本中不含条目副本。
- 条目 schema 含适用范围 / 重新验证 / 最后验证，且重新验证是可执行命令。
- 索引含泛化标签与依赖关系，且非空。
- 产物正文中不出现条目内容的复述，只出现标识引用。
- 自进化型在流程末尾有强制的应用记录产出，且「与描述不符之处」为必填。
- 核对型在每次功能开发完成后有强制的核对记录产出，且「哪些断言需要复核」为必填；核对结果区分吻合 / 不符 / 无法核对，无法核对不上报为偏差。
- 核对型的每条断言都有可定位的源码位置、可执行命令或可解析路径。
- 漂移探针存在、只读，且在任何耗时操作之前运行。
- 三类回流判定规则已写入管理器流程；有意遗忘机制存在。
- 闭环指标有明确口径，且漂移类型集中度被记录。
- 主产物是 skill 时与伴生件同处一个 plugin，主产物是文档时伴生件独立存放于 `harness/`；两种形态的分工都符合「组成与存放」表；知识库只出现一次，`legacy/` 中不含知识库副本。
- 每个 `SKILL.md` 的元数据通过 skill 校验脚本，且文档元数据挂在 `metadata:` 键下而非平铺。
