# 固定流程 Skill 范式

本文档定义固定流程 skill **必须约束的维度**与**治理机制**，用于产出具体场景的《固定流程 skill》。它不描述任何具体流程，描述的是把一条重复执行的流程固化成 skill 的方法、判断判据是否真的可执行的判据，以及让它在环境与流程演进中不静默失效的机制。

判据写不清、需要探索的流程见 [flexible_procedure_skill.md](../5-flexible-procedure/flexible_procedure_skill.md)；skill 自身失效之后的处理见 [skill_self_optimization.md](../7-skill-rsi/skill_self_optimization.md)。

## 1. 要回答的问题

重复固定流程人工处理时，时间开销繁重且结果不确定——同一类改动，两次执行的重跑范围、环境、结论口径都可能不同。这不是执行者能力问题，而是**流程本身没有被固化**。

因此本形态的核心不是写一份操作手册，而是**把判定逻辑写成可执行的规则**。它只回答一个问题：

> 面对一次改动，哪些阶段必须重跑，哪些可以复用？

由此展开三个可验证的目标：

| 目标 | 含义 |
|---|---|
| 判定可计算 | 「受影响」能被展开为具体的阶段 × 规格子集，不依赖判断者的经验 |
| 判定可审阅 | 判定先于执行产出，可记录、可事后对账 |
| 复用可积累 | 历史产物有明确的有效期依据，复用不会引入已失效的证据 |

**两条边界。** 它们决定一条流程该不该被固化成 skill：

- 每次都必须全量重跑的流程，需要的是一份**脚本**，不是固定流程 skill——skill 的价值完全来自可复用的部分。
- 复用边界无法从**改动清单 + 产物存在性**判定的，说明流程尚未被真正掌握，应回到生成层。凡是需要「看情况」「影响较大」才能判定的规则，都不是判据，是经验。

## 2. 建档判据与建档流程

### 2.1 必须同时满足的四条

1. 阶段数 ≥ 3，且阶段之间有产物依赖。
2. 存在历史产物，且「重跑 / 复用」的边界能写成判据。
3. 执行成本显著，使得多余重跑与漏跑都产生真实损失。
4. 验收目标可枚举。

第二条是分水岭。第二条不成立的，先不要建档——建出来的会是一份操作手册。

### 2.2 建档流程

人工完整走一遍流程并记录步骤与约束 → 标出判据 → 落成 skill → 补只读预检入口 → **用一次真实历史改动回放校验判据**。

最后一步最常被跳过，而它恰恰是唯一能证伪判据表的环节；没有它，判据表只是一份看起来合理的猜测。

回放所用的历史改动必须**同时包含「必须重跑」与「可以复用」两类阶段**。只含其中一类的改动无法证伪判据表：全量重跑的改动在任何判据表下都成立。

## 3. 必须约束的维度

生成物必须对下表每一行给出明确约定。

| 维度 | 约束什么 | 缺失时的后果 |
|---|---|---|
| 适用范围与响应契约 | 哪些请求触发；每次请求的第一份输出是什么 | skill 被不适用请求调用；跑错的范围在结果出来前不可见 |
| 阶段划分 | 阶段的产物依赖 DAG 与收敛点 | 无法回答某个阶段是否受影响 |
| 引用链 | 配置之间、配置与数据的引用关系 | 一次改动追不到受影响的阶段 |
| 路径与产物布局 | 产物的固定位置、权威产物与原始产物的区分 | 复用无从判定；旧证据被覆盖 |
| 基线规格 | 流程所服务的规格组合 | 「受影响」无法展开为具体子集 |
| 重跑判据表 | 变更类型 × 阶段的判定矩阵 | 退化为操作手册 |
| 受影响集合的展开 | 判据表中「受影响」的具体含义 | 表看似可判定，实际仍靠经验 |
| 执行环境与依赖基线 | 运行时、依赖基线、挂载与数据可见性、硬件分配 | 环境不可见，全部阶段的产物失去可比性 |
| 执行入口、顺序与前置条件 | 阶段入口、只读预检、资源互斥 | 判定无法执行，或执行了错误的配置 |
| 分析阶段 | 分析入口、数据源、配对与判定方法、产出物 | 结论不可信，且不会报错 |
| 分析目标清单 | 目标的来源、每条结论的判据与证据 | 分析漂移 |
| 产物分级 | 实测证据与 smoke 的边界 | smoke 被当作实测证据引用 |
| 反例与禁止项 | 已知误用与契约级禁止操作 | 同类误用重复发生 |
| 失效与漂移 | skill 过时的检测与上报 | skill 静默失真 |

## 4. 逐维度规范

每节给出三件事：**原则**、**为什么**、**生成时须填写什么**。

### 4.1 适用范围与响应契约

**原则**：写明两类内容——什么样的请求触发本流程，以及每次请求的**第一份输出**是什么。第一份输出通常就是重跑判定，且判定必须与执行分离：先报告判定，再按判定执行。

**为什么**：适用范围不明的 skill 会被不适用请求调用，产出一份格式正确但无意义的判定，并被后续引用为证据。判定与执行不分离时，跑错的范围在结果出来之前不可见。

**须填写**：

- 触发的请求类型；**明确排除的相邻请求类型**（尤其是最容易与之混淆的那一个）及排除理由。
- 第一份输出的确切形式：它的列、取值集合，且每一列都能追溯到判据表。
- 何时不再询问确认。固定流程若在每次执行前反复确认，就退化成了人工流程。
- 依赖缺失或契约不匹配时的行为：报告具体路径与恢复办法，**不得以「历史上成功过」为由继续执行**。

### 4.2 阶段划分

**原则**：阶段必须是**产物依赖的 DAG**，不是任务清单。每个阶段声明自己的输入、输出，以及输出中哪些成为后续阶段的输入。

**为什么**：只有阶段之间存在显式的产物依赖，「A 变了，B 是否受影响」才是可计算的。任务清单只能回答"接下来做什么"，回答不了"能不能跳过"。

**须填写**：

- 阶段清单与阶段间的产物依赖边，用数据流图表达（一侧输入、一侧输出）。
- **收敛点**：哪个阶段的产物是最终分析的直接输入。收敛点决定重跑代价的分布。
- 阶段数不宜多。两个阶段之间若不存在产物依赖，它们通常是同一个阶段。

### 4.3 引用链

**原则**：配置之间、配置与数据之间的引用关系逐级写明，使得从任意一个改动出发，能沿引用链追到它落在哪个阶段、影响哪些产物。

**为什么**：改动落在文件和配置上，判定要在阶段层面做出，中间的映射只能由引用链提供。引用链缺失时，"这个改动影响什么"只能靠重新读一遍流程。

**须填写**：

- 每一类配置的引用链，一直追到最终数据（顶层配置 → 阶段配置 → 数据）。
- 每类配置的位置，以及它归属哪个阶段。
- **生成物与执行物的一致性**：配置会被生成、复制或固化成命令，改掉源头不等于改掉实际被执行的那一份。须写明执行入口读取的是哪一份，以及如何验证两者一致。

### 4.4 路径与产物布局

**原则**：输入与输出有固定的根；输出布局区分**权威产物**与**原始产物**；历史产物视为只读。

**为什么**：复用判据的输入之一是"产物是否存在且仍然有效"，路径不固定则这条判据无从判定。权威与原始不分，新结果就可能覆盖旧证据，而覆盖之后旧证据无法恢复。

**须填写**：

- 各级根路径及其含义（代码仓库、实验根、配置根、数据根）。
- 目录布局：每一类产物落在哪里。
- 哪些是权威产物、哪些是原始产物，以及二者的关系。
- 新结果的命名规则（新的运行标识或新的输出目录）。
- **禁止的写操作**：覆盖权威产物、删除原始产物、用旧名字承载新结构。

### 4.5 基线规格

**原则**：列出流程所服务的**规格组合**，每个规格维度给出取值，每个规格组合给出一个稳定的名字。规格是「受影响集合」得以展开的坐标系。

**为什么**：只写"受影响"而不知道受影响的空间是什么，判据表就无法收敛到具体子集。规格同时是复用有效性的边界——跨规格的产物不可复用。

**须填写**：

- 规格维度清单（例如模型、硬件、运行模式、参数集）与各维度的取值。
- **独立单元**：哪些规格组合彼此独立，互不影响。
- **共享中间产物**：哪些规格组合共用同一份中间产物，改动其一即两者都受影响。

一个维度上的取值若每次运行都会变，它就不是规格，是运行参数。

### 4.6 重跑判据表

**原则**：「变更类型 × 阶段」的矩阵，每格取 **重跑 / 复用 / 不适用**。

**为什么**：这张表是 skill 的核心，也是它区别于操作手册的唯一标志。表中每一格都是一条可执行的判定规则；没有这张表，前面所有维度都只是背景介绍。

**须填写**：

- 变更类型的**封闭集合**，且每个类型都能由改动清单机械判定——改动路径、配置字段名、产物是否存在。不接受「影响较大」这类条件。
- 每格的取值。
- **版本断层行**：会让全部阶段同时失效的整类变更单列成行，并写明它为什么是全量失效。这类变更代价最高、也最容易漏；典型代表是外部依赖的大版本更换、硬件或拓扑更换。
- **无效果行**：明确写出不触发任何重跑的变更类型（例如只改文档或注释）。没有这一行，判据表会被读成"任何改动都要跑点什么"。

### 4.7 受影响集合的展开

**原则**：表中出现的每一个「受影响」，都必须在同表或邻接之处展开为**具体的子集表达式**——哪些规格单元、哪些阶段、哪些配置。

**为什么**：判据表里保留一个未展开的"受影响"，等于把判定重新交还给经验：表看起来可判定，实际不可判定。这是判据表最常见的失效方式——每一格都填了，但没有一格是机械可判的。

**须填写**：

- 展开规则：每一类变更在规格坐标系上落在哪些单元。
- **独立性声明**：某规格变化时另一规格不受影响，必须显式写出。不写等于"不知道"。
- 共享中间产物的说明：哪些阶段的产物被多个规格单元同时消费。

### 4.8 执行环境与依赖基线

**原则**：把执行环境当作流程的一个**被声明、被版本固定**的对象，而不是入口命令里的一截前缀。写明运行时与进入方式、依赖基线及其版本、挂载与数据可见性、硬件分配。

**为什么**：环境是判据表里最宽的一类失效源——它一变，全部阶段的产物同时失去可比性。而它对判定者恰恰不可见：一条形如「包装脚本 + 命令字符串」的入口把环境和命令裹在一起，读的人只看见命令。环境不被单独声明，就既无法在判据表里为它单列一行，也无法在复用旧产物时核对"当时的环境是不是现在这个"。

**须填写**：

- **运行时与进入方式**：用哪个解释器、容器或远端环境，从哪一层进去。入口命令里的环境前缀不构成声明——它要在这节里被展开成可核对的事实。
- **依赖基线**：基础镜像或环境名，加上依赖清单文件及其版本标识。依赖清单文件必须可寻址：修改它等同于修改环境。
- **挂载与数据可见性**：宿主路径与执行环境内路径的对应关系；哪些是**同一份数据**、哪些是复制。同一份数据出现在两个路径下时必须写明，否则两边的产物会被当成两个来源。
- **硬件分配**：设备可见范围、卡数与拓扑，以及它与 §4.5 规格维度中硬件项的对应关系。
- **环境变化的去向**：指明哪些环境项的改动属于 §4.6 的版本断层，会使全部阶段失效。

**边界**：这节声明环境**是什么**；变量如何送达执行处，属于 §4.9。

### 4.9 执行入口、顺序与前置条件

**原则**：每个阶段给出唯一入口；入口支持**只读预检**，在真实执行前展示将被解析出的实际配置与命令。同时给出阶段的执行顺序与每阶段的前置条件。

**为什么**：判定只有在能被执行时才有意义；预检在"判定 → 执行"之间加了一道可对账的环节，使生成物与执行物不一致这类错误在执行前暴露。前置条件不检查会让昂贵阶段的结果不可信——采集类阶段通常要求资源独占与干净状态。

**须填写**：

- 每阶段的入口命令与预检方式。
- **环境变量的作用域**：变量在哪一层进程边界内生效。入口若通过包装脚本、容器或子进程转发，宿主侧设置的变量可能根本到不了实际执行处，并会静默回退到默认值。须写明变量应设置在何处，以及如何验证它确实生效。
- 执行顺序表；每阶段的前置检查项（资源空闲、目录清洁、空间余量）。
- **资源互斥清单**：哪些阶段不能与其他负载并存。
- 扩展策略：先跑最小受影响子集，确认产物完整后再扩展到全量。一次性全量执行会让失败点无法定位。
- 执行前必须落盘的元信息：代码版本、配置、环境、产物标识、实际命令。没有这些，本次判定在事后不可对账。

### 4.10 分析阶段

**原则**：分析是流程的最后一个阶段，必须和其他阶段一样有明确的入口、输入、方法与产出，不能只留下一张分析目标清单。

**为什么**：分析阶段的失败不表现为报错，只表现为**结论不可信**。而它的三个部件又很容易寄居在别的维度里——入口被"每阶段的入口命令"接住，数据源被引用链接住，输出位置被目录布局接住；看起来处处有着落，实际没有一个维度以它为主体，于是**配对与判定方法**这类只属于分析的东西无处安放。

**须填写**：

- **分析入口**：命令，以及本次分析的运行标识（新标识，不复用旧标识）。
- **数据源**：读取哪些上游产物，各自对应 §4.2 收敛点上的哪个阶段。
- **配对与判定方法**：不同来源的产物如何对齐。至少写明配对键（不接受按文件名或序号配对）、内容不一致时降级到逻辑匹配的条件、配对失败如何记录（排除出汇总但保留诊断）、存在多个候选产物时如何选定权威来源并保留其余诊断。
- **误差口径**：报告哪些方向的误差（signed / absolute / relative）；小样本分位数的解释限制；哪些量属于不同层级，必须分别标注而不得合并。
- **产出物清单**：生成哪些表、图与报告，各自落在 §4.4 的哪个位置。

### 4.11 分析目标清单

**原则**：分析阶段逐条给出四元组：

```text
结论项 | 判据（可执行） | 证据（路径或命令） | 判定（通过 / 失败 / 不适用 + 原因）
```

**为什么**：分析阶段的漂移，根源不是目标没列全，而是**目标没有绑定证据**。缺少证据位的目标清单，执行者只能用印象填判定。

**须填写**：

- **目标的来源。** 每条结论项都要能指回它的出处，来源只有三类：**上游契约**（规范、接口约定、schema 与 metadata 约束）、**本次要验证的功能语义**（这次改动宣称做到了什么）、**参考指标**（无硬门槛，只用于观察趋势）。指不出出处的结论项是执行者自己挑的，应当删掉。
- 四元组清单。
- **硬门槛与参考指标分组**，不得混列。混列会诱使执行者为了让参考指标好看而放过契约问题。硬门槛组只接受判据可执行的目标：来自上游契约的，或来自功能语义但已写成可执行判据的（例如「四个方向存在非零完成证据」）；其余全部进参考指标组。
- 三条规则：证据必须是路径或命令，不是形容词；未完成项必须写原因（省略的条目在下一轮会变成「看起来通过」）；含糊的通过会摧毁信任，部分通过是有用的，含糊的通过不是。
- （可选）本次流程要得出的结论。流程若服务于一个阶段性目标，写明它可以避免执行者自行挑选结论。

### 4.12 产物分级

**原则**：流程产出的证据按强度分级——**实测 ground truth** 与 **smoke**（进程内或小规模的语义验证）。两者不可互相替代，汇报时必须标明每条结论来自哪一级。

**为什么**：存在低成本的 smoke 时，它会被当作廉价替代品去支撑本该由实测支撑的结论。这类替换不会报错，只会让结论失去证据基础，而表面上与真实验证毫无区别。

**须填写**：

- 各级别的产物清单与获取入口。
- 每个级别**不能支撑的结论**（写出否定面，而不是只写它能做什么）。
- 在响应契约中标注级别的方式。

### 4.13 反例与禁止项

**原则**：两条互补的清单——**反例清单**记录已知的误用及其纠正；**禁止项**以否定式给出任何情况下都不执行的操作。

**为什么**：固定流程的失败模式通常是**混用不同来源或不同级别的产物**，这类错误不在运行时暴露，只在解释结果时才被发现，而那时成本已经付出。禁止项则覆盖判据表覆盖不到的情形——判据表说的是"改了什么就跑什么"，禁止项说的是"无论改了什么都不做"。

**须填写**：

- 反例清单，每条含：错误做法 / 为什么错 / 正确做法。至少覆盖三类混淆：**版本来源混淆**（同名产物来自不同版本的流程）、**证据级别混淆**（smoke 与实测）、**口径混淆**（同一个数字在不同层级的不同含义，例如逻辑容量、物理占用、完成量、命中率）。
- 禁止清单，至少覆盖：不以「历史上成功过」为由强行执行；不删除或覆盖权威产物；不因耗时反复询问确认；不在契约不匹配时让下游做外推或截断。

### 4.14 失效与漂移

**原则**：分两层——**运行前只读校验**与**漂移上报**。

**为什么**：流程会过时：环境、命令、数据位置、分析目标都在变。校验让 skill 中硬编码的事实每次运行前被验真；上报让过时本身成为可积累的信号。漂移必须上报而不是就地修改——就地修改会让漂移失去记录价值，而且执行层并不具备判断"这是过时、环境变化还是一次性问题"所需的信息。

**须填写**：

- 只读校验项清单与校验命令。
- 三分类的处理方式：可自动修正的（修正并记录）、契约层面的不匹配（**立即停止并报告，不得回退到宽松判定**）、skill 自身写错的（上报，交演化层）。
- 漂移记录的格式与去向。

## 5. 治理机制

固定流程 skill 的失效方式是**静默失真**，不是报错。以下三项是让它保持有效的机制：

**5.1 判定可对账。** 每次执行都留下判定记录：判定结论、依据、实际执行的子集。判定与执行不一致时，事后能定位是判据错了还是执行跳过了判据。

**5.2 复用必留依据。** 复用历史产物时记录所复用产物的路径与版本标识。没有这条记录，复用一旦出错，影响范围无法确定——所有引用过它的结论都要重新审。

**5.3 漂移上报，不就地修改。** 任何「skill 描述与实际不符」都记录为信号，而不是在本次执行中悄悄绕过。

## 6. 存放、元数据与校验

生成物是 **skill**，不是说明文档。它按 [docs-paradigm.md](../0-docs-paradigm/docs-paradigm.md) §2 存放于：

```text
docs/developer-guide/harness/<skill-name>/
├── SKILL.md          # 主文件
└── references/       # 可选：细节下沉的引用文件
```

**固定流程 skill 必须配一份伴生 skill。** 它由 [skill_self_optimization.md](../7-skill-rsi/skill_self_optimization.md) 生成，角色是**自进化型**：在流程的各阶段之间挂捕获点，并在每次流程结束时产出应用记录，把「判定错了」「复用失效」「与描述不符」回流成条目。伴生件与主流程 skill 同处一个 plugin，按 [flexible_procedure_skill.md](../5-flexible-procedure/flexible_procedure_skill.md) §6 的 plugin 布局组织；上面的布局是只有一个 skill 时的退化情形。

**为什么必须有。** §4.14 已经要求「漂移上报，不就地修改」，但上报需要一个接收方。没有伴生件时，漂移只能被就地绕过——本次运行看起来成功了，下一个人从同一个地方再踩一次。而判据表越精确，它的有效期就越依赖环境不变，这一点正是伴生件要盯住的。

选这个位置的理由与范式自身同源：判据表的输入是**改动清单**，而改动清单只能覆盖同一版本控制内的内容。skill 与它约束的源码处在同一次变更里，判据才追得上代码。

`harness/` 的收录判定标准是「服务于 AI 开发流程本身，不描述产品行为」。由此两条：

- skill 里不写产品行为说明、架构决策与接口约定——那些属于 `design/`、`standards/`、`reference/`，skill 按标识引用，不复制内容。
- skill 描述的是**怎么跑、怎么判定**，不是**系统是什么**。

**仓库内的这份是唯一源。** agent 实际加载的副本由安装入口（安装脚本或符号链接）指向它；不得直接编辑已安装的副本，否则下一次安装会静默丢弃修改。

**元数据分两套，不得混写。** [docs-paradigm.md](../0-docs-paradigm/docs-paradigm.md) §4 要求正式文档声明五个元数据字段，但 harness 下的 `SKILL.md` **不属于那类文档**：它首先是一个被程序加载的 skill，frontmatter 的字段集合是封闭的，多一个键就装不上。两套字段的归属如下：

|  | skill 元数据 | 文档元数据 |
|---|---|---|
| 字段 | `name` / `description` / `license` / `allowed-tools` / `metadata` / `compatibility` | `status` / `authority` / `owner` / `updated` / `applies_to` |
| 定义于 | skill 规范，由校验脚本强制 | docs-paradigm §4 |
| 读者 | 加载器与模型——决定是否选中这个 skill | 人——判断是否过时、归谁维护、覆盖什么范围 |
| 变更时机 | 描述的适用范围变化时 | 内容有任何改动时 |

把文档元数据的字段平铺进 frontmatter，校验脚本会把它当成拼写错误，skill 直接装不上：

```text
Unexpected key(s) in SKILL.md frontmatter: authority, status, updated.
Allowed properties are: allowed-tools, compatibility, description, license, metadata, name
```

文档元数据要写，就挂在合法的 `metadata` 键下——这个键的内容不被校验：

```yaml
---
name: <skill-name>                                    # 给加载器与模型
description: <触发条件；模型据此决定是否选中本 skill>
metadata:                                             # 给人与治理流程
  status: current
  authority: normative
  owner: project maintainers
  updated: YYYY-MM-DD
  applies_to: "<具体模块、命令或版本范围>"
---
```

**安装前必须跑校验。** 不得凭印象添加字段：把「何时使用」写成 frontmatter 中未声明的键，同样会让 skill 装不上。生成后先校验，通过再安装。

其余要求：

- 描述字段要写出**触发条件**，使 skill 在正确的时候被选中；描述中不得出现会被解析的尖括号字符。
- skill 中的路径、配置名、命令**必须与源码一致**；docs-paradigm §6 的「只用源码中存在的精确拼写、不创造源码中不存在的新概念」在此同样适用。
- 篇幅较长时按「主文件 + 引用文件」组织，主文件只保留每次都要用的部分。

## 7. 验收

生成物满足以下全部条件才算合格：

- §1 的核心问题有唯一答案：给定一次改动能产出重跑集合，且该集合不依赖判断者经验。
- 触发条件与排除条件都已写明，排除条件包含最容易混淆的相邻请求类型。
- 响应契约规定了第一份输出，判定与执行分离，且明确了何时不再确认。
- 阶段构成产物依赖的 DAG 而非任务清单；收敛点已标明。
- 引用链可从任意配置追到数据；生成物与执行物的一致性有验证方式。
- 路径与产物布局区分权威产物与原始产物；禁止的写操作已列出。
- 基线规格的维度与取值明确；独立单元与共享中间产物已声明。
- 执行环境已声明：运行时与进入方式、依赖基线及其版本标识、挂载与数据可见性、硬件分配；环境项的改动在判据表中的去向已指明。
- 重跑判据表存在，变更类型是封闭集合且机械可判，含版本断层行与无效果行。
- 表中每一处「受影响」都已展开为具体子集；独立性声明非空。
- 每阶段有唯一入口与只读预检；环境变量作用域已写明；执行顺序与前置条件齐全。
- 分析阶段有独立约定：入口、数据源、配对与判定方法、误差口径、产出物清单；配对键不是文件名或序号。
- 分析目标清单为四元组；每条结论项都能指回三类来源之一；硬门槛组只含判据可执行的目标；证据均为路径或命令。
- 产物分级明确，各等级不能支撑的结论已写出。
- 反例清单覆盖三类混淆；禁止清单非空。
- 只读校验项与漂移处理的三分类已写明。
- 生成物存放于 `docs/developer-guide/harness/<skill-name>/`；仓库内的是唯一源，安装入口已写明。
- 已按 §6 配自进化型伴生 skill：捕获点挂在流程的阶段之间，应用记录为强制产出，§4.14 的漂移有明确的接收方。
- 元数据通过 skill 校验脚本；skill 中的路径与命令与源码一致。
