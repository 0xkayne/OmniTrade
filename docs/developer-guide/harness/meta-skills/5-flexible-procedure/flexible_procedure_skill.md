# 非固定流程 Skill 范式

本文档定义非固定流程 skill **必须约束的维度**与**治理机制**，用于产出具体场景的《非固定流程 skill》。它不描述任何具体流程，描述的是把一条**尚无固定流程**的工作固化成 skill 的方法、判断「某处该不该被判为未知」的判据，以及让本轮探索的产物在下一次被直接命中的机制。

判据已能写清的流程见 [fixed_procedure_skill.md](../4-fixed-procedure/fixed_procedure_skill.md)；被生成的 skill 的自我优化伴生件见 [skill_self_optimization.md](../7-skill-rsi/skill_self_optimization.md)。

## 1. 要回答的问题

非固定流程人工处理时，同一件事会被反复探索——接入第二个同类对象时，第一次踩过的坑会再踩一遍。这不是执行者记性差，而是**第一次的探索没有留下可被命中的产物**：结论留在当时的对话里，没有变成下次能被查到的条目。

因此本形态的核心不是写一份探索指南，而是**把「已探索」变成一种可判定的状态**。它只回答一个问题：

> 这次任务里，哪些部分已经有依据、可以直接照做，哪些部分还没有依据、必须重新探索——以及探索的产物存到哪里，使下一次它变成「有依据」？

由此展开三个可验证的目标：

| 目标 | 含义 |
|---|---|
| 未知可判定 | 「没有依据」是检查得出的判定，不是感觉；判定先于执行产出，可记录、可事后对账 |
| 探索有产物 | 每次探索都留下能被下次命中的条目，而不是只留下本次的结论 |
| 收窄可度量 | 「需要探索的部分」是否在变少是可观察的；收窄到位的部分移交给固定流程 |

**两条边界。** 它们决定一条工作该不该被固化成非固定流程 skill：

- 判据已经能写清的部分（改动清单 + 产物存在性可判），属于**固定流程 skill**，不属于本文档——不要用探索的自由度去覆盖本可以固定的部分。
- 探索的产物若只对本次任务有意义（一次性问题），它不进知识库。带着这类产物的知识库会被一次性问题淹没，与空库等价。

第二条同时划定了建档的前提：**没有「下一次」的工作不需要本文档**。

## 2. 建档判据与建档流程

### 2.1 必须同时满足的四条

1. 目标已知，达到目标的步骤未知——否则它是一条固定流程。
2. 存在一份可枚举的**已知目录**，使得「未知」能被判定出来。
3. 存在一个**真值源**，可以判定本次是否对齐。
4. 同类任务会有下一次，使知识库的命中成为可能。

第二条是分水岭。第二条不成立时，判定「未知」所依据的参照系并不存在，未知套着未知，本形态退化为一般的探索，没有可固化的东西。

### 2.2 建档流程

人工完整走一遍并记录实际路径 → 枚举**已知目录** → 标出这次走到的未知处及其处理方式 → 确定真值源 → 落成 skill → 补只读预检入口 → **用一次真实历史任务回放校验**。

最后一步最常被跳过。它要回答的是一个具体问题：**把当时已积累的条目交给当时的执行者，哪些探索本可以省掉**。答不出来，说明条目尚未积累到能被命中的程度，或条目的触发条件写成了只有作者能懂的形式。

回放所用的历史任务必须**同时包含「命中已有条目」与「必须重新探索」两类部分**。只含其中一类的任务无法证伪本流程：全是未知的任务在任何判定方式下都成立。

## 3. 必须约束的维度

生成物必须对下表每一行给出明确约定。

| 维度 | 约束什么 | 缺失时的后果 |
|---|---|---|
| 适用范围与响应契约 | 哪些请求触发；第一份输出是什么 | skill 被不适用请求调用；未知在执行到一半时才暴露 |
| 稳定骨架 | 阶段序列与各阶段的可变部分 | 每轮组织方式不同，产物与捕获点无处挂载 |
| 已知目录 | 判定「未知」所对照的封闭类别集合 | 「未知」不可判定，只能凭熟悉程度 |
| 未知判定 | 「未知」为一等返回值，以及它的判定形式 | 新东西被伪装成最相似的旧东西 |
| 真值源与解释源的分离 | 谁是对齐标准，谁只用来解释意图 | 用更易读的那一侧当验收依据，结论与目标错位 |
| 未知处理协议 | 从原始信息到研究型任务的固定步骤 | 用实现型任务冒充研究型任务 |
| 交付物契约 | 每次运行必须产出的具名交付物 | 结论有了，证据与待验证项没有留下 |
| 知识库与准入 | 唯一源、准入判据、去重判据 | 库被一次性问题稀释，等价于空库 |
| 技能拆分与路由 | 规模上限、拆分依据、映射与路由表 | 单一 skill 过长，执行者在调用中漂移 |
| 证据规则 | 每条结论的可定位出处与缺口标记 | 结论与猜测不可区分；缺口被错误的源填上 |
| 校验门禁 | 通过 / 失败 / 证据不足三值 | 「通过」被稀释成「没发现明显问题」 |
| 反例与禁止项 | 已知误用与契约级禁止操作 | 同类误用重复发生 |
| 收窄、移交与漂移上报 | 覆盖度表、移交判据、漂移去向 | 流程长期停留在全量探索且无人察觉 |

## 4. 逐维度规范

每节给出三件事：**原则**、**为什么**、**生成时须填写什么**。

### 4.1 适用范围与响应契约

**原则**：写明两类内容——什么样的请求触发本流程，以及每次请求的**第一份输出**是什么。第一份输出是**已知 / 未知的判定**，不是执行动作。

**为什么**：若 skill 一被触发就进入执行，未知部分会在执行到一半时才暴露，而此前按错误假设产出的结论无法回收。判定先行还有第二个作用：判定记录可以被事后对账，执行过程不能。适用范围不明的 skill 则会被不适用请求调用，产出一份格式正确但无意义的判定，并被后续引用为证据。

**须填写**：

- 触发的请求类型；**明确排除的相邻请求类型**（尤其是最容易与之混淆的那一个）及排除理由。
- 第一份输出的确切形式：它的列、取值集合，以及每一列如何从已知目录与知识库得出。
- 何时不再询问确认。
- 依赖缺失或真值源不可达时的行为：报告具体位置与恢复办法，**不得回退到「按上一次的做法」继续执行**。

### 4.2 稳定骨架

**原则**：内容可变，**阶段的序列不变**。写明始终存在的那几个阶段，并声明每个阶段哪些部分是固定的、哪些部分依本次任务而定。

**为什么**：没有固定骨架的 skill，每次运行的组织方式都不同，于是上一轮产出的产物在下一轮没有固定的位置可被消费，知识库也无从挂载捕获点。骨架是让「变化」可被度量的参照系。

**须填写**：

- 阶段清单与顺序。阶段数不宜多——两个阶段之间若不存在产物依赖，它们通常是同一个阶段。
- 每个阶段声明：**固定部分**（每次都要做的动作）与**可变部分**（依本次任务而定的内容）。
- 骨架中必须显式包含三个位置：**判定**（已知 / 未知）、**未知处理**、**知识回灌**。这三处是本形态区别于一般流程的地方，不能寄居在别的阶段里。

### 4.3 已知目录

**原则**：给出一份**可枚举的类别集合**，作为判定「未知」的参照系。每个类别给出它的判定条件，且每条判定条件都要能由输入数据机械判定。

**为什么**：没有目录时，「未知」无法被判定——执行者只能凭熟悉程度判断某处算不算新东西，而熟悉程度不可对账。目录同时是知识库条目的挂载点：条目按类别索引，命中才可能发生。

**须填写**：

- 类别的封闭清单及各自的判定条件。不接受「影响较大」这类条件。
- 类别与知识库条目索引的对应关系。
- 目录为空或尚不完整时的声明方式。此时几乎所有内容都会落到「未知」，这是正常的起点，不是失败；但必须写明，否则会被读成「没有未知」。

### 4.4 未知判定

**原则**：**「未知」是一个一等返回值**，与已知类别并列，且它的判定必须机械可执行。分类器在任何情况下都必须能返回它。

**为什么**：分类器的默认行为是落回最近的已知分支。这会把手里的新东西伪装成熟悉的旧东西，而错误不会在分类时暴露——它要等到按旧分支产出的结论被证伪时才出现，那时成本已经付出。被迫返回「未知」比被迫选一个近似类别更有价值。

**须填写**：

- 判定的具体形式：对照目录逐项检查、任一项无匹配即把该处标记为未知。
- **禁止的替代行为**：不得用「最相似类别 + 差异说明」代替「未知」；不得因为「大体上像」而跳过标记。
- 未知的输出粒度：落在哪个类别、哪个子项上，而不是「整体是新的」。粒度决定后续处理协议的作用范围。

### 4.5 真值源与解释源的分离

**原则**：声明确认本次是否对齐的**唯一判定来源**，并把它与只用来理解意图的来源分开。

**为什么**：这类工作中几乎总是存在两个来源——一个描述「它想做什么」，一个决定「它实际怎么做」。两者必然有差异，而只有后者能作为验收依据。不声明这一条时，执行者会用更易读的那一个作为对齐标准，产出的结论看起来完整，却与实际目标错位。这是本形态中代价最高、也最不易自查的一类错误。

**须填写**：

- 真值源是什么、解释源是什么，各自的可读取入口。
- 两者的差异出现在哪些方面**是未知的**，必须在本轮中实际分析后确定——**不得预先枚举成清单**。枚举会把它降级成一份勾选项，而漏掉的部分不会提示自己存在。
- 每个结论必须标明它依据的是哪一侧。

### 4.6 未知处理协议

**原则**：为「未知」给出固定的处理步骤，从原始信息出发，到产出**研究型任务**为止。

**为什么**：未知处的失败模式不是做错，而是**用实现型任务冒充研究型任务**——在还没理解新东西该如何建模时，就生成了「照着做」的指令；执行者据此写出看起来合理、却无法验证是否对齐的代码。研究任务的产物是理解与建模方案，不是代码。

**须填写**：

- 固定的处理步骤：原始信息收集（提取完整的数据流，逐步标注进出与生命周期）→ 从固定轴做第一性原理分析 → 映射到既有抽象（需要哪些新建、哪些扩展）→ 生成研究型任务。
- **分析轴是固定的**，各场景使用同一组轴（典型的三个轴是存储、计算、数据流）；轴上得到的内容才依任务而定。
- **研究型任务与实现型任务的区分规则**，以及研究型任务模板中必须含有的字段。
- 本轮若仍未确定：产出**临时条目**并在条目上标明状态，**不得**据此生成实现型任务。

### 4.7 交付物契约

**原则**：每次运行产出的不是一份说明，而是一组**具名的交付物**，其构成是封闭的、可逐项核对的。

**为什么**：非固定流程最容易出现的失败是「做完了但缺东西」——结论有了，但支撑结论的证据、待验证项、受影响位置没有留下，下游只能从对话里捞。写成契约后，缺项是可检出的；不写成契约，缺项只会表现为下游的返工。

**须填写**：

- 交付物清单：每项的名称、位置、必备字段。
- 哪些交付物必须在本轮结束前产出；未完成项必须**显式标注为待验证**，不得省略条目本身。

### 4.8 知识库与准入

**原则**：声明存在一个**持续增长、唯一**的知识库，条目按标识被引用。准入的判据是：条目必须描述「**在什么条件下会发生什么**」，而不是「这次发生了什么」。

**为什么**：知识库的价值全部来自被下一次命中。一次性问题混进来会稀释它——被淹没的条目与不存在的条目等价。保持库有效的手段不是事后清理，而是入库时的判据。

**须填写**：

- 知识库的位置与单一源约束。**条目的字段、状态机与索引由 [skill_self_optimization.md](../7-skill-rsi/skill_self_optimization.md) 定义，此处只声明它存在并引用，不重复其内容。**
- **准入判据**：可复用约束与一次性问题的区分方式。
- **去重判据**：与已有条目「触发条件完全覆盖」「部分重叠」「条件相同而约束不同」三种情形各自的处置。
- 被拒绝的条目及其理由要留下记录，否则同一件事会被反复提案。

### 4.9 技能拆分与路由

**原则**：主文件给出**规模上限**，超出时按**分析维度**拆分，不按执行步骤拆分；拆分必须同时产出映射文档与路由表。

**为什么**：单一 skill 过长时，执行者会在调用中漂移——读到中段时前段的约束已经淡出，于是出现「按后半段的做法覆盖前半段的禁令」这类错误。而拆分只有按分析维度做时，每个子 skill 才是一个自洽的分析单元，可以独立加载；按执行步骤拆开，会让每个子 skill 都缺少完整的判断依据。

**须填写**：

- 规模上限，给出具体数字（行数或段数），不能写成「尽量短」。
- **拆分映射文档**：每个子 skill 承接原文本的哪一段。
- **路由表**：哪一类知识或请求归哪个子 skill，以及新增内容时应更新哪一个。路由表要写明自己的更新时机——新增条目时先按类别路由，再更新承接它的子 skill。
- 主文件只保留骨架与指针；细节下沉到引用文件，主文件始终可读。

### 4.10 证据规则

**原则**：每条实质结论记录**可定位的出处**（文件、类、函数、命令），并显式标出缺口。

**为什么**：这类工作的结论会被下游直接消费，而下游没有能力重新判断。没有出处的结论与猜测不可区分。更隐蔽的是**用错误的源填空**——缺口处若允许从解释源补齐，结论会带上一段看起来有依据、实际与本任务判定源无关的内容，且不会有任何提示。

**须填写**：

- 出处的形式：精确拼写、可被检索定位。
- 缺口的标记方式，以及缺口在交付物中的位置。
- **降级路径**：真值源不可达时走哪条次要路径，以及降级必须在该结论上留痕（标明它来自次要路径）。

### 4.11 校验门禁

**原则**：在执行之前设一道独立的校验，取值为 **通过 / 失败 / 证据不足** 三值。

**为什么**：两值判定会逼执行者在证据不全时选一个，「通过」于是被稀释成「没发现明显问题」。第三值把「结论可能对但证据不在」单独拿出来，使它既不被算作通过、也不被算作失败，而是变成一项待补的工作。

**须填写**：

- 校验项清单，以及每项对应的交付物。
- 三值各自的判定条件；**证据不足不得被视为通过**。
- 失败时的返回内容：阻塞项，以及需要修改的具体位置——不是一句「不完整」。

### 4.12 反例与禁止项

**原则**：两条互补的清单——**反例清单**记录已知的误用及其纠正；**禁止项**以否定式给出任何情况下都不执行的操作。

**为什么**：这类流程的失败模式通常是**混用不同来源或不同级别的产物**。它不在运行时暴露，只在解释结果时才被发现，而那时成本已经付出。禁止项还覆盖判定覆盖不到的情形——判定说的是「这类内容该走哪条路」，禁止项说的是「无论哪条路都不做」。

**须填写**：

- 反例清单，每条含：错误做法 / 为什么错 / 正确做法。至少覆盖三类：**用解释源代替真值源**、**用最相似类别代替「未知」**、**把一次性问题入库**。
- 禁止清单，至少覆盖：不把知识库条目的内容复制进 skill（只引用标识）；不在未知处直接生成实现型任务；不以「上次这样做过」为由跳过判定；不在真值源不可达时让下游做外推。

### 4.13 收窄、移交与漂移上报

**原则**：维护一张**覆盖度表**（对应 §4.3 的每个类别：已有条目数、覆盖程度、还缺什么），并声明移交条件与漂移去向。

**为什么**：本形态的价值在于收敛——探索过的部分应当越来越不需要重新探索。没有覆盖度表时，这一点不可观察，流程会长期停留在全量探索而无人察觉。而覆盖度到位的类别，其做法已经能被写成判据，继续留在探索形态里是纯粹的成本，且会拖长每一次运行。

**须填写**：

- 覆盖度表的字段与更新时机（每次运行结束时更新）。
- **移交判据**：某个类别的条目达到什么状态、其判据能被写成什么形式时，该类别移交给固定流程 skill；移交后本 skill 只保留指向它的引用，不保留做法本身。
- 漂移的去向：skill 描述与实际不符时，交 [skill_self_optimization.md](../7-skill-rsi/skill_self_optimization.md) 生成的伴生 skill 处理，**不就地修改**。

## 5. 治理机制

非固定流程 skill 的失效方式是**退化成探索日志**——每次运行都从头开始，产出的东西越来越长、越来越像记录而不像判据。以下三项是让它保持有效的机制：

**5.1 判定可对账。** 每次运行留下判定记录：哪些部分被判为已知、依据是什么、哪些被判为未知。判定与执行不一致时，事后能定位是目录写错了还是执行跳过了判定。

**5.2 条目先于做法。** 一类内容要进入 skill 的骨架，必须先有对应条目；不得先把做法写进 skill、事后再补条目。次序颠倒会让 skill 里出现无出处的说法，而无出处的说法在下一轮无法被复现或修正。

**5.3 覆盖度可观察。** 每次运行结束更新覆盖度表。覆盖度长期不上升，说明条目写成了只有作者能懂的形式，或准入判据执行得太宽——两者都会让库里的条目看起来很多、实际命中不了。

## 6. 存放、元数据与校验

生成物是一个 **plugin**，至少包含两个 skill：**主流程 skill 由本文档生成**，**自优化伴生 skill 由 [skill_self_optimization.md](../7-skill-rsi/skill_self_optimization.md) 生成**。它按 [docs-paradigm.md](../0-docs-paradigm/docs-paradigm.md) §2 存放于：

```text
docs/developer-guide/harness/<plugin-name>/
├── .claude-plugin/plugin.json   # 插件清单，加载器读它
├── skills/
│   ├── <领域>-<主流程>/SKILL.md  # 本文档生成
│   └── <领域>-<自优化>/SKILL.md  # skill_self_optimization.md 生成
├── references/                  # 共享：知识库、路由表、拆分映射、细节文件
│   └── <知识库>/
└── legacy/                      # 可选：拆分前的 skill 定义，只读
```

选这个位置的理由与固定流程同源：知识库的命中靠**触发条件与代码事实的匹配**，而代码事实只能来自同一版本控制内的内容。skill 与它约束的源码处在同一次变更里，条目才追得上代码。

单个 skill 是只有一个成员的退化情形：去掉 `plugin.json` 与 `skills/` 这一层，`harness/<skill-name>/SKILL.md` 直接由安装入口指向。

**为什么必须有一个伴生 skill。** §1 的两个目标——探索有产物、收窄可度量——都要求有一个接收方：没有伴生件，本轮发现的约束只能留在本次对话里，覆盖度表也没有人更新，流程会永远停在第一轮的水平。非固定流程没有固定判据可依赖，对抗过时唯一的依托就是这条回流通道。

`harness/` 的收录判定标准是「服务于 AI 开发流程本身，不描述产品行为」。由此两条：

- skill 里不写产品行为说明、架构决策与接口约定——那些属于 `design/`、`standards/`、`reference/`，skill 按标识引用，不复制内容。
- skill 描述的是**怎么判断、怎么探索**，不是**系统是什么**。

**两个 skill 的分工，不得互相越界。**

| 事项 | 归属 |
|---|---|
| 骨架与阶段划分、已知目录、未知判定与处理协议、真值源、交付物契约、校验门禁、覆盖度与移交 | 本文档生成的主流程 skill |
| 条目字段与状态机、索引结构、捕获点位置、漂移探针、回流的三类判定 | skill_self_optimization.md 生成的自优化 skill |
| 知识库的物理位置与单一源约束 | 两边共同声明，措辞不得冲突 |

**知识库在 plugin 内只出现一次。** `legacy/` 只存放**拆分前的 skill 定义**，**不得存放知识库副本**。冻结副本会立刻与持续增长的源分叉——出现两个同名目录、其中一处还指向已经不存在的位置，是这类副本的典型症状。历史条目本来就留在知识库里，不需要第二份。

**元数据分三套，不得混写。** [docs-paradigm.md](../0-docs-paradigm/docs-paradigm.md) §4 要求正式文档声明五个元数据字段，但 harness 下的 `SKILL.md` **不属于那类文档**：它首先是一个被程序加载的 skill，frontmatter 的字段集合是封闭的，多一个键就装不上。plugin 清单又是第三个 schema。

|  | skill 元数据 | plugin 清单 | 文档元数据 |
|---|---|---|---|
| 字段 | `name` / `description` / `license` / `allowed-tools` / `metadata` / `compatibility` | `name` / `version` / `description` / `author` / `keywords` | `status` / `authority` / `owner` / `updated` / `applies_to` |
| 定义于 | skill 规范，由校验脚本强制 | plugin 规范 | docs-paradigm §4 |
| 读者 | 加载器与模型——决定是否选中这个 skill | 插件加载器——决定是否装载这个 plugin | 人——判断是否过时、归谁维护、覆盖什么范围 |
| 写在哪 | `SKILL.md` 的 frontmatter | `.claude-plugin/plugin.json` | `SKILL.md` 的 `metadata:` 下 |

把文档元数据的字段平铺进 skill frontmatter，校验脚本会把它当成拼写错误，skill 直接装不上：

```text
Unexpected key(s) in SKILL.md frontmatter: authority, status, updated.
Allowed properties are: allowed-tools, compatibility, description, license, metadata, name
```

文档元数据要写，就挂在合法的 `metadata` 键下——这个键的内容不被校验：

```yaml
---
name: <skill-name>                                    # 给加载器与模型
description: <触发条件；模型据此决定是否选中本 skill>
metadata:                                             # 给人与治理流程
  status: current
  authority: normative
  owner: project maintainers
  updated: YYYY-MM-DD
  applies_to: "<具体模块、命令或版本范围>"
---
```

**安装前必须跑校验。** 不得凭印象添加字段：把「何时使用」写成 frontmatter 中未声明的键，同样会让 skill 装不上。plugin 内每个 `SKILL.md` 都要单独校验，生成后先校验、通过再安装。

其余要求：

- 描述字段要写出**触发条件**，使 skill 在正确的时候被选中；描述中不得出现会被解析的尖括号字符。
- skill 中的路径、配置名、命令**必须与源码一致**；docs-paradigm §6 的「只用源码中存在的精确拼写、不创造源码中不存在的新概念」在此同样适用。
- 篇幅较长时按「主文件 + 引用文件」组织，主文件只保留每次都要用的部分；引用文件放在 plugin 的 `references/` 下共享，不各自复制一份。

## 7. 验收

生成物满足以下全部条件才算合格：

- §1 的核心问题有唯一答案：给定一次任务能产出已知 / 未知的划分，且该划分不依赖判断者经验。
- 触发条件与排除条件都已写明，排除条件包含最容易混淆的相邻请求类型。
- 响应契约规定了第一份输出是判定而非执行动作，且明确了何时不再确认。
- 稳定骨架的阶段序列固定，每阶段区分了固定部分与可变部分，且骨架中显式含有判定、未知处理、知识回灌三个位置。
- 已知目录是可枚举的封闭集合，每类判定条件机械可执行；目录不完整时有显式声明。
- 「未知」是一等返回值，判定形式明确，禁止用最相似类别替代；未知的输出粒度落在类别或子项上。
- 真值源与解释源已分离并各自指明入口；两者差异的清单未被预先枚举；每条结论标明所依据的一侧。
- 未知处理协议的步骤固定，分析轴固定；研究型任务与实现型任务有区分规则。
- 交付物契约是封闭清单，含名称、位置与必备字段；未完成项标注为待验证。
- 知识库声明为唯一源；准入判据与去重判据已写明；条目 schema 不在此处重复。
- 技能规模上限是具体数字；拆分依据是分析维度，且有拆分映射文档与路由表。
- 证据规则要求可定位出处；降级路径存在且在结论上留痕。
- 校验门禁为三值；证据不足不被视为通过；失败返回阻塞项与具体位置。
- 反例清单覆盖三类混淆；禁止清单非空。
- 覆盖度表存在且更新时机明确；移交判据已写明；漂移上报不就地修改。
- 生成物存放于 `docs/developer-guide/harness/<plugin-name>/`；主流程 skill 与自优化 skill 分工不越界；知识库在 plugin 内只出现一次；`legacy/` 不含知识库副本。
- 每个 `SKILL.md` 的元数据通过 skill 校验脚本；plugin 清单字段独立；skill 中的路径与命令与源码一致。
