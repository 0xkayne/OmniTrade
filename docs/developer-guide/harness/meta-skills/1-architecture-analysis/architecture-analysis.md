# 架构分析

本文档定义**在功能开发开始之前**对目标模块做架构分析的方法：分析什么、产出什么、产出物放在哪里、如何与代码保持一致。

文档系统本身的布局、命名与元数据规则见 [docs-paradigm.md](../0-docs-paradigm/docs-paradigm.md)；本文只负责**架构分析这一步**。

## 1. 触发时机

**任何模块级功能开发开始之前。**

功能开发的正确性取决于对现有架构边界的理解。跳过分析直接编码，会导致三类可预见的失败：

1. 撞上未被发现的既有约束。
2. 破坏模块之间或模块内部的不变量。
3. 重复实现已经存在的能力，或在新代码里重建一套与既有划分不一致的结构。

分析针对**模块**，不针对整个系统。一次分析要能回答：这个模块由什么构成、它依赖谁、谁依赖它、一次执行在它内部如何展开。

纯文档、纯注释、不涉及模块边界与数据流的改动，不触发本文档的流程。

## 2. 产物

**一张图 + 一份 workflow 文档，成对，缺一不可。**

图给出结构与接口，文档给出因果与流程。只有图，读者会猜两个模块为什么相连；只有文字，读者会在长文档里迷路。

图的可读性与信息密度以 [`examples/`](examples/) 下的两份样例为实际标准：以模块为节点，标注模块之间的关系类型、对外暴露的接口，以及被替换或将被替换的部分。新产出的图应当与样例处于同一粒度和同一信息密度量级，而不是更粗略的框图。

## 3. 分析的层次

按粒度分层，每层回答一个独立问题。**不必每层都做，但必须明确本次做到哪一层，并写进文档的范围声明。**

| 层 | 回答的问题 |
|---|---|
| 全局 | 系统由哪些模块构成，主干数据如何流动 |
| 模块 | 模块内部有哪些对象，谁拥有谁，对外接口在哪 |
| 链路 | 一次运行或一次请求按时间展开发生了什么 |
| 符号 | 对象级职责与调用关系 |

功能开发通常至少需要「模块」与「链路」两层：模块层给出边界，链路层给出改动会落在时序的哪一步。只做模块层，改动的影响范围仍然说不清。

## 4. 图

- **图由代码推导**，不由手绘，也不让模型直接生成图像文本。图上每个节点必须对应代码中真实存在的符号。
- **每条边必须标注语义**，说明两端是调用、持有、数据流还是替换关系。无标注的边不出现。
- **同一层的视觉编码在全项目保持一致**，使读者不依赖图例即可识别层次；图上不画图例，语义由本文档与既有样例承担。
- 单图节点数量控制在一屏可读完的规模。超出则拆成多张分层的图，而不是缩小字号。

## 5. Workflow 文档

固定骨架，顺序不变：

1. **范围声明** —— 覆盖哪个模块、做到哪一层，以及**不覆盖什么**。
2. **结论** —— 核心设计取舍，能被单独摘出当摘要。
3. **对象树** —— 自顶向下的分解。
4. **组件职责** —— 「职责」与「不负责什么」两列。后者不可省：明确不负责什么，是抑制越界修改最有效的手段。
5. **流程** —— 初始化顺序（含为什么必须是这个顺序）、运行时序、关键路径。
6. **状态与不变量** —— 状态机、身份与命名空间、修改代码时不得被破坏的约束。
7. **失败门禁** —— 哪些情况设计上就应当直接失败，以及失败时给出什么信息。区分「有意为之的失败」与「尚未验证的范围」。
8. **源码位置** —— 图上每个对象对应的代码位置。

第 6、7 节直接对应 docs-paradigm.md §1 要求的「修改代码时哪些约束不能被破坏」。第 4 节的「不负责什么」一列，与第 7 节共同构成 AI 编码时的边界约束。

## 6. 存放与元数据

产出物是正式文档，遵循 [docs-paradigm.md](../0-docs-paradigm/docs-paradigm.md)：

- **Workflow 文档**存于 `docs/developer-guide/design/`，文件名 `<域>-<主题>.md`；域前缀取自该规范登记的封闭集合，不得使用集合之外的域。
- **图**是静态资源，存于 `docs/assets/`，由文档正文相对引用。
- 文档必须带元数据声明：`status` / `authority` / `owner` / `updated` / `applies_to`，且 `applies_to` 要写出具体模块或版本范围。
- **`status: current` 只描述已实现的内容。** 分析过程中发现的、代码里尚不存在的设计意图，必须单独标记为 `proposal` 并说明批准条件，不得混入当前实现的描述。
- 术语与标识符使用源码中的精确拼写；不得为了让文字更好懂而创造源码中不存在的新状态或新层级。

一个模块的架构分析通常同时覆盖「为什么这样设计」与「具体怎么实现」两层。只写理论而不描述对应源码，或只罗列源码而不说明取舍，都不算合格。

## 7. 与代码的一致性

架构文档最大的风险不是写错，而是写对之后代码变了。让不一致可发现：

- 文档记录**分析所依据的代码版本**与**未覆盖范围**。后者不是可选项——它区分「文档没提」和「系统里没有」。
- 图与文档必须能**双向对账**：图上每个元素可定位到源码；源码中读者需要知道的符号都在图上或文档中有位置。
- 源码与文档不一致时，以源码为准，并修正文档或明确记录代码缺陷；不得在文档中保留两个都像正确答案的说法。
- **重绘触发**：涉及该模块的变更被合入；组件职责边界变化；不变量或失败门禁增减。
- 发现文档与实际不符时，**记录信号并交 [skill 自我优化](../7-skill-rsi/skill_self_optimization.md) 处理，不就地修改**——就地修改会让漂移本身失去记录价值。

文档的生命周期（修改、删除、重建的判定）遵循 docs-paradigm.md §5。

## 8. 消费

1. AI 开始编码前，先读本文档，再读目标模块对应的 `design/` 文档，**不要从读代码开始**。
2. 做架构决策读模块层；做时序或状态推理读链路层；写具体代码时才回到符号层。
3. **引用任何对象时，必须能给出源码位置。** 给不出，说明分析没有做到位，应回到模块层或符号层补齐。
4. 架构文档描述的是职责边界与设计意图；接口签名以源码为准，冲突时按 §7 处理。

## 9. 伴生核对 skill

本文档的产物是**图 + workflow 文档**，它们本身不能执行，因此按 [skill_self_optimization.md](../7-skill-rsi/skill_self_optimization.md) 生成的是**核对型**伴生 skill，而不是自进化型。

**为什么必须有。** §7 已经写明「不一致要可发现」，靠的是「重绘触发」这类约定——但约定不会自己触发。架构文档最大的风险不是写错，而是**写对之后代码变了**；而读图的人正是依据图来判断改动落点的，失效的图会让每一次判断都错在一个看不见的地方。

**它做什么。** 每次功能开发完成后，把 §7 的双向对账真正跑一遍，产出偏差条目：

| 核对对象 | 判定依据 |
|---|---|
| 图 → 源码 | 图上每个节点是否仍对应可定位的真实符号；是否出现未标注的边 |
| 源码 → 图 | 读者需要知道的符号是否都在图上或文档中有位置 |
| 骨架完整性 | §5 的八个段落是否齐全，「不负责什么」一列是否非空 |
| 职责边界 | §5 第 4 节的职责表与图上的模块边界是否仍然一致 |
| 不变量与失败门禁 | §5 第 6、7 节列出的约束是否仍成立、是否增减 |
| 范围声明 | 文档记录的代码版本与未覆盖范围是否仍然准确 |
| 重绘触发 | §7 列出的三类触发条件是否已经发生 |

**三条约束。**

- 每条断言必须指向可定位的源码符号；定位不到的断言**单列**，**不上报为偏差**。
- 核对在**功能开发完成后**触发。§7 的重绘触发回答的是「什么时候该重绘」，核对回答的是「怎么发现它已经该重绘了」——前者是判据，后者是执行者。
- 偏差只产出**条目草案**，改图与改文档由管理器判定后执行；这与 §7「记录信号并交 skill 自我优化处理，不就地修改」是同一条规则。

**存放。** 伴生 skill 独立存放于 `docs/developer-guide/harness/<skill-name>/`；图与 workflow 文档留在 `docs/developer-guide/design/` 与 `docs/assets/`，不搬进 `harness/`。

## 10. 验收

一份合格的架构分析产出满足：

- 图与 workflow 文档成对存在，且能从 `developer-guide/` 索引到达，无 orphan page。
- 图上每个节点对应可定位的真实符号；无未标注的边。
- 文档含全部骨架段落，且「不负责什么」一列非空。
- 文档声明了分析所依据的代码版本与未覆盖范围。
- 双向对账通过：图 → 源码、源码 → 图各检查一遍。
- 文档中的对象名与图上节点名一一对应，无同物异名。
- 元数据完整；未实现的内容标记为 `proposal`，未混入 `current` 的描述。
- 示例与结论中引用的命令、路径、配置键在源码中真实存在。
- 已按 §9 生成核对型伴生 skill：核对清单覆盖 §7 的双向对账与重绘触发，每条断言可定位到源码符号，偏差只产出条目草案。
