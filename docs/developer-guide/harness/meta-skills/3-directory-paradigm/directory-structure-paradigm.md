# 代码目录结构范式

本文档定义目录结构规范**必须约束的维度**与**治理机制**，用于产出具体项目的《代码目录结构规范》。它不描述任何具体项目的目录树，描述的是产生目录规则的方法、判断一份目录结构是否合格的判据，以及让结构在代码演进中不被侵蚀的机制。

命名规则见 [naming-conventions.md](../2-naming-convention/naming-conventions.md)；本文只负责**结构**，两者不重复对方内容。

## 1. 结构要回答的问题

目录结构的问题不是"文件放得不好看"，而是**从目录看不出谁依赖谁**。一份合格的目录结构，应当只盯着目录、不读任何代码，就能回答三个问题：

| 问题 | 用于 |
|---|---|
| 这个模块属于哪一层？ | 判断一个新模块该放哪里 |
| 它被允许依赖谁，被谁依赖？ | 判断一次改动会波及哪些包 |
| 删掉它会不会波及别处？ | 判断哪些代码能安全删除 |

**这三条同时是本文档的边界。** 凡是无法只看目录回答的规则，都不属于结构规范——它属于命名规范或编码规范，不应写入生成物。这条约束防止目录规范退化成一份什么都管、实际什么都管不住的文档。

## 2. 必须约束的维度

生成物必须对下表每一行给出明确约定。

| 维度 | 约束什么 | 缺失时的后果 |
|---|---|---|
| 分层模型 | 有哪些层、层的顺序 | 无层级参照，新模块无处安放 |
| 允许边集 | 哪些跨层依赖合法，方向如何 | 只有"上层依赖下层"这类不可判定的原则 |
| 同层隔离 | 同层包之间是否可互相导入 | 层内耦合，分层退化为命名习惯 |
| 环 | 循环依赖如何处理 | 环把两层绑成一团，无法单独理解或删除 |
| 横向层 | 跨层可用的能力放在哪里 | 工具代码散落各层，或寄生在某一业务层 |
| 隔离区 | 待删除/待隔离代码放在哪里 | 旧代码混在现役目录中，无法一次性移除 |
| 目录收录规则 | 每个目录收什么、不收什么 | 边界靠个人判断，同一职责落在多处 |
| 目录与文件命名 | 包名、文件名、文件规模 | 名字重复表达层信息；文件混杂多职责 |
| 测试目录对应 | 测试目录如何对应源码目录 | 测试按类型分目录，与源码结构脱节 |
| 现状与目标 | 文档描述的是现状还是目标 | 目标被当成现状读，偏差无人处理 |
| 迁移路径 | 从现状到目标的阶段与顺序 | 一次性重排，无法定位失败点 |
| 可执行检查 | 结构规则如何被机械验证 | 规则只能靠人工审查，必然失效 |

## 3. 逐维度规范

每节给出三件事：**原则**、**为什么**、**生成时须填写什么**。

### 3.1 分层模型

**原则**：把顶层模块划分为有序的若干层，并给出层与层的依赖方向。每层用一句话说明它的职责边界。

**为什么**：没有层，就没有判断新模块归属的依据；没有方向，就无法判断一次导入是否合法。

**须填写**：层的清单（层名 / 一句话职责）、层序、以及依赖方向的图示。层数不宜多——超过五层通常说明把职责切得太碎，而不是划分得更准确。

### 3.2 允许边集与依赖方向

**原则**：合法的跨层依赖必须枚举成一张**封闭的允许边集**：哪些层可以依赖哪些层，一条不多。规则表之外的新增依赖一律非法。

**为什么**："上层可以依赖下层""不要产生不合理依赖"这类表述无法判定，也无法检查。只有枚举成表，规则的合规性才是可判定的——这正是 §1 三条问题能成立的前提。

**须填写**：允许边的完整清单。

**反向依赖必须单独论证。** 依赖方向通常自下而上，但存在合法的例外（典型是适配器需要构造上层领域对象）。这类例外必须：

1. 在允许边集中显式列出；
2. 说明它为什么合法（通常是端口-适配器方向）；
3. 说明**相反方向为什么被禁止**。

三者缺一，例外就会变成先例。

### 3.3 同层隔离

**原则**：同一层的包之间不得互相导入，除非在允许边集中显式允许。

**为什么**：层内互相导入会让分层退化成命名习惯——两个包名义上同层，实际已经合并，但目录上看不出来。

**须填写**：同层隔离的规则；若有例外，逐条列出并说明理由。

### 3.4 环的禁止

**原则**：任何 A 依赖 B、B 依赖 A 同时成立都视为错误，无例外。

**为什么**：环把两个模块绑成一个不可分的整体——无法单独理解、单独测试、单独删除。环也会让"改动波及范围"这个问题失去答案，直接破坏 §1 的第二、三个问题。

**须填写**：环的检测方式（见 §3.12）。若当前存在环，必须在 §3.10 的偏差清单中列出，并在 §3.11 给出解环方案。

### 3.5 横向层

**原则**：跨层共用的能力（观测、日志、通用工具）集中在一个横向层。**任何层都可以依赖它，它不依赖任何业务层。**

**为什么**：不设横向层时，这类代码会散落到各层，或寄生在某一业务层里，使那一层被所有其他层间接依赖，依赖图随即失去层次。

**须填写**：横向层的名称与收录范围；以及"它不依赖任何业务层"这条约束的检查方式。

### 3.6 隔离区

**原则**：需要保留但不应参与新架构的代码（待删除的旧实现、兼容层）集中到一个隔离区，并满足 **只进不出**：隔离区之外没有任何文件导入它。

**为什么**：旧代码分散在现役目录中时，无法整体删除，也无法判断某段代码是否还有人用。集中成"只进不出"的一棵树，就可以在任何时刻一次性移除。

**须填写**：隔离区的名称；"只进不出"的检查方式；隔离区是否参与 §3.7 的目录收录规则（通常不参与）。

### 3.7 目录收录规则

**原则**：每个目录都给出**收**与**不收**两栏。

**为什么**：只写"收什么"不足以判断边界——真正的争议总发生在边界附近。写出"不收什么"，并在必要时记录某一项被划到别处的原因，才能让后来者不必重新讨论同一个问题。

**须填写**：每个目录的「收」与「不收」；以及对**边界项**的归属决定与理由。边界项的处理是本节的实质内容，只列显而易见的成员项不构成收录规则。

### 3.8 目录与文件命名

**原则**：

- 包名与层名一致；一个层一个包，不拆不并。
- 文件名表达一个主要职责。
- **层已经由目录表达的信息，不在文件名中重复。**
- 文件规模设上限；超限时先确认是否混装了多个职责，而不是直接拆分。

**为什么**：目录是唯一的位置信息载体，文件名重复它只会制造冗余。文件规模上限的价值不在数字本身，而在于**它是"职责混杂"的信号**——超限是需要复查结构的提示，不是拆分的指令。

**须填写**：包名的形态约定；文件名的形态约定；规模上限；以及当前超限文件的清单（它们同时是 §3.10 偏差清单的一部分）。

### 3.9 测试目录对应

**原则**：测试目录**按模块镜像源码目录**，不按测试类型划分。测试类型通过标记（marker）表达，不通过目录表达。

**为什么**：按类型分目录时，测试的位置与它所测的模块无关——定位某个模块的测试需要跨多个类型目录查找，模块被删除或重构时也无法按目录清理。类型是测试的属性，不是它的归属。

**须填写**：测试目录与源码目录的对应规则；测试类型的表达方式；无对应源码目录的测试（端到端、共享夹具）放在哪里。

### 3.10 现状与目标的差距

**原则**：文档必须**显式声明自己描述的是现状还是目标**。当代码尚未符合规范时，说明它是目标，并列出实测偏差。

**为什么**：一份混合了"应该怎样"与"实际怎样"的文档，会被读成对现状的描述。读者据此判断代码位置时会持续出错，而错误不会以任何方式提示自己存在。

**须填写**：声明语句；偏差清单（每条含位置与实测数据）；偏差的判定日期。偏差必须实测，不得凭印象列出。

### 3.11 迁移路径

**原则**：从现状到目标分阶段进行，**每阶段结束后测试必须全绿**；先做低风险的搬运，再做需要改逻辑的解耦。

**为什么**：一次性重排会让失败无法定位。分阶段且每阶段可验证，才能把"结构调整"与"行为改变"两类风险分开处理。

**须填写**：阶段表（阶段 / 内容 / 风险 / 验证方式）；**存在顺序依赖的阶段必须显式标注**；涉及行为改变的阶段必须单独列出，并说明需要补充的测试。

### 3.12 可执行检查

**原则**：每条可机械判定的结构规则都应附一条可执行命令。

**为什么**：结构规则靠人工审查必然失效——它们检查的是"没有发生的事"（没有非法导入、没有环），而这类问题不会主动暴露。

**须填写**：依赖方向、隔离区、环、文件规模等规则的检查命令。无法附命令的规则必须显式标注为人工审查项。

## 4. 治理机制

结构规范的失效方式是**被绕过**，而不是被违反。以下两项是让它保持有效的机制：

**4.1 新增即更新。** 新增模块时必须同时更新目标目录树与依赖边集，并确认原有规则仍然成立。目录树与边集是规范正文，不是附录。

**4.2 偏差可追溯。** 已记录的偏差在处理完成后从偏差清单移除；新增偏差必须重新实测。不得保留已经修复的偏差条目，也不得长期保留未处理的偏差而不说明原因。

## 5. 存放与元数据

生成物是正式文档，遵循 [docs-paradigm.md](../0-docs-paradigm/docs-paradigm.md)：

- 存放于 `docs/developer-guide/standards/`，与同目录的命名规范等文档互相引用。
- 必须带元数据声明：`status` / `authority` / `owner` / `updated` / `applies_to`。`applies_to` 要写出具体的目录范围与测试目录对应关系。
- 目录名、包名、模块路径使用源码中的精确拼写；不得为了好懂而创造源码中不存在的层级（这会与 §3.8 的"不重复表达层信息"直接冲突）。
- `status: current` 只描述已经成立的结构。目标结构若尚未达成，须按 §3.10 显式声明，不得作为当前结构陈述。

## 6. 伴生核对 skill

本文档的产物是**目录结构规范文档 + 目标目录树 + 允许边集 + 偏差清单**，它本身不能执行，因此按 [skill_self_optimization.md](../7-skill-rsi/skill_self_optimization.md) 生成的是**核对型**伴生 skill，而不是自进化型。

**为什么必须有。** §3.12 已经说明「结构规则靠人工审查必然失效——它们检查的是『没有发生的事』」。而 §1 的三条问题（模块属于哪一层、允许依赖谁、能否安全删除）只在**下一次改动的落点判断**中被使用；那时依据的是规范写的结构还是代码的实际结构，两者一旦分叉，判断会持续出错，而且没有任何机制会提示。

**它做什么。** 每次功能开发完成后，跑一遍 §3.12 的检查命令，产出偏差条目：

| 核对对象 | 判定依据 |
|---|---|
| 允许边集 | §3.2 的边集之外是否出现了新的跨层依赖 |
| 环 | §3.4：是否出现 A 依赖 B、B 依赖 A 同时成立 |
| 同层隔离 | §3.3：同层包之间是否新增了导入 |
| 隔离区 | §3.6「只进不出」：隔离区之外是否有文件导入它 |
| 横向层 | §3.5：横向层是否反向依赖了业务层 |
| 目录收录 | 是否出现 §3.7「不收」清单中的内容 |
| 文件规模 | §3.8 的规模上限：超限文件是否增加 |
| 测试目录对应 | §3.9：测试目录是否仍镜像源码目录 |
| 偏差清单 | §3.10 的偏差是否已实测、是否有长期未处理项 |

**三条约束。**

- 每条断言必须指向可定位的目录、包或导入边；检查命令必须**真的能跑通**且与当前源码布局一致。跑不通的命令**单列**，**不上报为偏差**——命令失效和结构违规是两件事。
- 核对在**功能开发完成后**触发，不看开发规模：新增一个文件也可能引入一条非法依赖。
- 偏差只产出**条目草案**，改规范正文、目录树或边集由管理器判定后执行；不得在核对时就地改规范。

**存放。** 伴生 skill 独立存放于 `docs/developer-guide/harness/<skill-name>/`；规范正文留在 `docs/developer-guide/standards/`，不搬进 `harness/`。

## 7. 验收

生成物满足以下全部条件才算合格：

- §1 的三条问题都能只看目录回答；文档中没有需要读代码才能判定的规则。
- §2 的十二个维度全部有明确约定。
- 允许边集是封闭枚举，不是原则性描述；每条反向依赖都附有合法性论证及其禁止方向。
- 每个目录同时给出「收」与「不收」，且至少处理了若干边界项的归属。
- 目标目录树与允许边集同时存在，且互相一致（树上出现的每个包都在边集中有位置）。
- 测试目录与源码目录的对应规则明确；测试类型不通过目录表达。
- 文档显式声明描述的是现状还是目标；若是目标，偏差清单已实测并标注日期。
- 迁移阶段表齐全，顺序依赖已标注，行为改变类阶段单独列出。
- 可机械判定的规则均附检查命令，或已标注为人工审查项。
- 与同目录的命名规范互相引用，且不重复对方内容。
- 元数据完整，`applies_to` 写出具体范围。
- 已按 §6 生成核对型伴生 skill：核对清单覆盖允许边集、环、隔离区与偏差清单，跑不通的命令单列而不上报为偏差。
