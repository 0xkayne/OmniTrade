# 命名规范范式

本文档定义命名规范**必须约束的维度**与**治理机制**，用于产出具体项目的《命名规范》。它本身不给出任何具体名字，给出的是产生名字的规则、判断名字是否合格的判据，以及让规范在代码演进中保持有效的方法。

代码结构规范见 [directory-structure-paradigm.md](../3-directory-paradigm/directory-structure-paradigm.md)；本文只负责**名字**，两者不重复对方内容。

## 1. 规范要回答的问题

1. **看到一个名字，能不能判断它属于哪个功能模块？**
2. **能不能保证它不被误用、不被同名符号混淆？**

由此展开三个可验证的目标：

| 目标 | 含义 |
|---|---|
| 归属可推断 | 从符号名或它的位置，能定位到负责它的模块 |
| 冲突可发现 | 同名不同物、同物不同名都能被机械检出 |
| 语义可对账 | 名字与源码中的实际概念一一对应，不存在只在文档里成立的名字 |

**命名规范不是风格偏好。** 凡是无法用一条命令或一次检索判断的规则，都不是规范，是建议；这类内容不应写入生成物。

## 2. 必须约束的十个维度

生成物必须对下表每一行给出明确约定。任何一行留作"视情况而定"，规范即不成立。

| 维度 | 约束什么 | 缺失时的后果 |
|---|---|---|
| 符号形态 | 各符号类别的大小写与分隔 | 同一类别多种写法，检索与重构不可靠 |
| 单位与语义类别 | 量纲、标识性、时点性是否进入名字 | 数值被误用，且不会报错只会算错 |
| 归属的表达 | 归属由位置表达还是由名字表达 | 名字膨胀；模块前缀之间互相冲突 |
| 全局唯一性 | 公开符号是否全项目唯一 | 同名不同物，import 时被静默遮蔽 |
| 术语唯一性 | 一个概念是否只有一个正式名称 | 同义词扩散，检索漏检 |
| 模块词根 | 模块内符号共享哪组词族 | 无法一眼看出归属 |
| 保留后缀 | 后缀是否只表示一种角色 | 后缀跨模块换意思，线索失效 |
| 函数名形状 | 函数名是否表达动作与作用对象 | 动作不明，宾语靠猜 |
| 易混名 | 相近名字是否被显式区分 | 相近名字互相替换 |
| 有意例外 | 例外是否被登记且不扩散 | 例外扩散成事实标准 |

## 3. 逐维度规范

每节给出三件事：**原则**、**为什么**、**生成时须填写什么**。

### 3.1 符号形态

**原则**：每个符号类别有唯一的大小写与分隔约定，类别之间不重叠。

**为什么**：检索与重构依赖形态的可预测性。形态不唯一时，一次按模式的检索必然漏检。

**须填写**：符号类别清单及各自的形态。类别至少覆盖：类、函数与方法、变量、常量、布尔值、类型别名、枚举值、私有符号、测试。

### 3.2 单位与语义类别进入名字

**原则**：名字必须携带读者无法从上下文可靠推断的信息——量纲、标识性、时点性。这类信息必须成为名字的一部分，不能依赖注释或调用点推断。

**为什么**：这类信息一旦缺失，误用不会产生任何错误，只会产生错误的结果。

**须填写**：本单位与语义类别后缀表；以及禁止使用的裸名清单（那些看似自明、实际量纲不明的名字）。

### 3.3 归属由位置表达，不由名字表达

**原则**：符号的归属由它所在的容器（包、目录、命名空间）表达；名字不重复表达位置信息。

两条禁止：

- **不把模块名写进符号名。** 限定词已经由容器给出，重复一次不增加信息，只制造缩写黑话。
- **不为区分而加层级词。** 层级由位置表达，不由名字表达。

**为什么**：在名字里重复位置信息，会创建源码中并不存在的层级，并使同一概念出现多个名字。

**须填写**：容器的实际层级；本项目需要禁止的层级词清单。

### 3.4 公开符号全局唯一

**原则**：公开的类、类型别名与模块级函数在全项目内唯一。

**为什么**：重复的公开名在引用时被静默遮蔽——问题不在定义处暴露，而在运行时才显现。

**须填写**：唯一性检查命令；冲突时的消歧规则。

消歧规则的通用形式：**用"拥有该概念的领域主体"消歧，不用模块名。** 模块名消歧等于把 §3.3 禁止的做法换个理由重新引入。

**检查命令必须真的能跑**，且必须与项目的实际源码布局一致。无法执行的检查命令等同于没有检查。

### 3.5 一个概念一个正式名称

**原则**：每个领域概念只有一个正式名称，其余写法列为禁用同义词。

**为什么**：同义词会让检索漏检——搜到一个名字，拿不到这个概念的全部实现，而漏掉的部分不会以任何方式提示自己存在。

**须填写**：正式术语表（正式名称 / 禁用同义词 / 说明）；新概念的登记位置。

**硬约束**：新概念必须先在登记位置定义，再改代码。不得在某个局部模块中临时命名。

### 3.6 模块词根

**原则**：每个模块拥有一组词根，模块内的公开符号应含有本模块的词根。

**关键**：**词根取自领域，不取自模块名。** 词根来自模块名时，名字就会变成模块前缀，回到 §3.3 已经禁止的做法。

**为什么**：这是"一眼看出归属"的主要机制，也是在不加模块前缀的前提下仍能判断归属的补偿手段——两者是一组配套规则，缺任一条，另一条都会失效。

**须填写**：模块清单，以及每个模块的词根表（词根 / 符号）。

**边界规则**：

- 跨模块共用的词根必须显式声明归属，说明各模块各自的含义。
- 某模块专有的角色词必须标注"其他模块不得复用"。

### 3.7 保留后缀

**原则**：后缀是保留词。一个后缀在全项目只表示一种角色，不得跨模块换意思。

**为什么**：后缀是读者判断符号性质最快的线索。一旦同一后缀在不同模块表示不同角色，这条线索整体失效，读者必须逐个查证。

**须填写**：后缀表（后缀 / 唯一含义 / 现有符号）。**新增后缀必须先登记。**

**边界**：登记时若发现已有后缀含义重叠，必须合并或明确各自边界，不得并存两个含义相近的条目。

### 3.8 函数名形状

**原则**：模块级函数名采用 `<动词>_<宾语>`，宾语取自本模块词根或领域术语。

**为什么**：只写动词的名字在跨模块调用时无法判断作用对象；只写宾语的名字无法判断产生的副作用。

**须填写**：动词表（动词 / 用途）；宾语的取值范围。

**例外机制**：无宾语的函数必须逐个登记，并说明为什么在该作用域内宾语是唯一且显然的。**新增无宾语函数必须同样登记。**

**固定形状的函数族**：注册、构造、解析、格式转换这类有稳定前缀的函数族，应在规范中固定其形状，使同一族的新函数不需要重新讨论命名。

### 3.9 易混名对照

**原则**：名字相近但含义不同的符号必须显式列出，禁止互相替换或简化。

**为什么**：相近名字的混淆不会报错，只会产生难以定位的行为差异。这类问题不会自己浮出来，只能靠显式对照防止。

**须填写**：易混名表（名字 / 位置 / 含义）；针对裸名与泛化名的禁令。

同节可一并登记：已废弃的别名、仅允许作为面向用户的说明别名而不得进入代码的名字。

### 3.10 有意例外

**原则**：不按规范改造的命名必须显式声明，且必须限定不扩散。

**为什么**：未登记的例外会扩散成事实标准——每一个新符号都可以援引某个未登记的例外，最终规范只剩形式。

**须填写**：例外类别与各自的约束。需要覆盖的常见类别：

| 类别 | 约束 |
|---|---|
| 历史代码 | 保留原名以免破坏兼容；同时声明**新增代码不得进入这些位置** |
| 外部接口适配 | 可沿用外部术语以保证对接；同时声明**外部术语不得扩散到领域层** |
| 局部作用域 | 泛化名仅在极小的局部作用域允许；跨层参数必须使用具体名称 |

## 4. 治理机制

规范的失效方式不是写错，而是被绕过。以下四项是让规范保持有效的机制，缺一项规范都会在若干次变更后失效。

### 4.1 可机械判定的检查

每条可机械判定的规则都应附一条可执行命令，并与项目的源码布局保持一致。无法附命令的规则，要么改写成可判定的形式，要么明确标注为**人工审查项**——不得混在可判定规则里。

### 4.2 登记表

例外、新增后缀、新增无宾语函数都必须登记。**登记表是规范正文的一部分，不是附录。** 允许"不加登记就直接使用"的规范，等价于没有规范。

### 4.3 定名流程

新增任何公开符号之前：

1. 检查全局唯一性（§3.4）。
2. 确认含有本模块词根（§3.6），或该符号已登记为例外（§3.10）。
3. 后缀取自保留后缀表（§3.7）；需要新后缀时**先登记再使用**。
4. 检查是否落入易混名（§3.9）。
5. 涉及新概念时，先在术语登记位置定义（§3.5），再改代码。

### 4.4 改名的影响面

改名会同时影响引用、测试、对外输出与文档。**必须在同一次变更内全部更新**，不得留下指向旧名的注释、文档或测试。

规范中须写明改名后运行的验证命令。

### 4.5 迁移记录

规范落地过程中产生的改名按表记录：原名 / 新名 / 位置 / 原因。

记录的作用是为后续判断提供依据——同类冲突再次出现时，可以直接沿用已确立的消歧结论。迁移完成后，已完成的记录不属于当前规范，按 [docs-paradigm.md](../0-docs-paradigm/docs-paradigm.md) §5 处理。

## 5. 存放与元数据

生成物是正式文档，遵循 [docs-paradigm.md](../0-docs-paradigm/docs-paradigm.md)：

- 存放于 `docs/developer-guide/standards/`，与同目录的代码结构规范等文档互相引用。
- 必须带元数据声明：`status` / `authority` / `owner` / `updated` / `applies_to`。`applies_to` 要写出具体的符号范围（哪类符号、位于哪些目录），不得使用"全部系统"这类无法验证的描述。
- 术语与标识符使用源码中的精确拼写；不得为了让文字更好懂而创建源码中不存在的新概念或新层级（§3.3 在文档层的对应约束）。
- `status: current` 只描述已采用的约定。尚未改造完成的部分必须写入 §3.10「有意例外」并标注迁移状态，不得作为当前规则陈述。

## 6. 伴生核对 skill

本文档的产物是**命名规范文档 + 三类登记表**，它本身不能执行，因此按 [skill_self_optimization.md](../7-skill-rsi/skill_self_optimization.md) 生成的是**核对型**伴生 skill，而不是自进化型。

**为什么必须有。** §4.1 已经要求「每条可机械判定的规则附一条可执行命令」，但这些命令默认在**写代码时**被想起来。命名规范失效的方式恰恰是**没人想起来查**：新符号被就地起名，检查命令一次也没有运行，而重名、同义词、未登记后缀这几类问题都不会报错，只会在检索和重构时漏检。

**它做什么。** 每次功能开发完成后，跑一遍 §3.4 / §3.5 / §3.7 / §3.8 / §3.9 / §3.10 对应的检查命令，产出偏差条目：

| 核对对象 | 判定依据 |
|---|---|
| 全局唯一性 | §3.4 的检查命令：是否有重复的公开类、类型别名、模块级函数 |
| 术语唯一性 | 是否出现禁用同义词（§3.5 正式术语表右列） |
| 模块词根 | 新增公开符号是否含有本模块词根，或已登记为例外 |
| 保留后缀 | 是否出现未登记的后缀（§3.7） |
| 无宾语函数 | 是否有未登记的无宾语函数（§3.8） |
| 易混名 | 易混名对照表中的名字是否被互相替换（§3.9） |
| 例外不扩散 | §3.10 登记的例外类别是否被新增代码侵入 |
| 登记表自身 | 登记表中列出的符号是否仍存在于源码中 |

**三条约束。**

- 每条断言必须指向可定位的源码符号；检查命令必须**真的能跑通**且与当前源码布局一致。跑不通的命令**单列**，**不上报为偏差**——命令失效和规则被违反是两件事。
- 核对在**功能开发完成后**触发，不看开发规模：一次改名同样要跑 §4.4 的验证命令。
- 偏差只产出**条目草案**，改规范正文或登记表由管理器判定后执行；不得在核对时就地改规范。

**存放。** 伴生 skill 独立存放于 `docs/developer-guide/harness/<skill-name>/`；规范正文留在 `docs/developer-guide/standards/`，不搬进 `harness/`。

## 7. 验收

生成物满足以下全部条件才算合格：

- §2 的十个维度全部有明确约定，无"视情况而定"。
- 每条可机械判定的规则附有可执行命令，且命令与源码布局一致。
- 例外、保留后缀、无宾语函数三类登记表齐全。
- 正式术语表与禁用同义词表非空。
- 易混名对照表非空。
- 模块词根表中，词根取自领域而非模块名；跨模块共用词根已声明归属。
- 与同目录的代码结构规范互相引用，且不重复对方内容。
- 元数据完整，`applies_to` 写出具体范围。
- 规范中出现的符号名与源码中的实际拼写一致。
- 已按 §6 生成核对型伴生 skill：核对清单覆盖三类登记表与全部检查命令，跑不通的命令单列而不上报为偏差。
